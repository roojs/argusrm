## Purpose

- 🔷 Block the controller window: a left nav, a page on the right, dialogues on top.
- 🔷 The first page to build is Scripts. `Script` and `ScriptRepository` are already callable. [7.1](7.1-tasks-implementation.md).
- 🔷 The window opens on Scripts.
- 🔷 Dashboard, Assets, Tasks, and Monitoring stay in this plan. They are the picture the aims walk through.
- 🔷 Assets are the machines and the software. Tasks are the manual way to make work. Monitoring is the lists of things to look out for.
- ℹ️ The window is already `Argus.Controller.Window`. The body is the connected label. This plan replaces that label.
- ℹ️ Task rows, drafts, approval, and one-task-many-machines are [7.0](7.0-tasks.md). Those calls are ready too. The Tasks page is the next page after Scripts.
- ℹ️ Programs are not stored yet. [3.0 Phase 3](3.0-server.md). Dashboard, Assets, and Monitoring wait on that.
- ℹ️ A plugin that registers a nav entry is the last section. The first window is one piece.
- 🚫 This plan does not name widget classes or new tables.

## Shell

- 🔷 Left nav picks a place. The right side shows that place.
- 🔷 Open places sit as tabs on the right. The nav highlights the tab in front.
- 🔷 A dialogue covers the page. It is how a row is edited.
- 🔷 A list page runs top to bottom: title action bar, grid, grid action bar, data view.
- 🔷 The title action bar is the page title, the filters, and actions that make a new row.
- 🔷 The grid action bar is the bulk actions for the ticked rows. Update all sits here.
- 🔷 The data view is the segments under that bar. The page ends there.
- 🔷 On Scripts, the grid action bar calls the script RPCs.
- 🔷 On the later pages, a work button creates a task. The Running tab is where that task is watched.
- 🔷 Closing the window still quits. The cog menu stays: deregister, register agent, register controller.

## Selection

- 🔷 The generic select-all is a narrow tick column on the left of every grid.
- 🔷 The column header is a tick. It selects every row in the current filter, including rows scrolled off the screen.
- 🔷 The header tick again clears that selection.
- 🔷 A mixed header mark means some rows in the filter are ticked.
- 🔷 The column is on a phone, a tablet, and a desktop. A tablet is touch, so it uses the same column as a phone.
- 🔷 The tick column stays on screen while the other columns scroll sideways.
- 🔷 Ticking a row adds it to the bulk selection. Activating the rest of the row shows that row in the data view.
- 🔷 With no ticks, the grid action bar acts on the row in the data view.
- 🔷 With ticks, the bar acts on the ticked rows and shows how many.
- 🔷 A pointer device also has a right-click menu on the grid. The menu says Select all, and it lists the same bulk actions as the bar.
- 🔷 The right-click item is the words Select all. The tick stays in the column.
- 🔷 Phone and tablet do not need that menu. The header tick is the select-all they use.

```
phone / tablet                         desktop (pointer)
+---------------------------+          +---------------------------+
| [x] name    machines      |          | [x] name    machines      |
| [x] nginx   12            |          | [x] nginx   12            |
| [ ] curl    40            |          | [ ] curl    40            |
+---------------------------+          +---------------------------+
 header tick = select all              header tick = select all
                                       right-click also: Select all
```

## Scripts

- 🔷 This is the page to build. The calls below are already in [7.1](7.1-tasks-implementation.md).
- 🔷 The title action bar picks the library. `scripts/` is repository id `0`. A clone comes from `ScriptRepository.list`.
- 🔷 The grid is `Script.list` for that id. Columns are the path and the filetype.
- 🔷 The data view is `Script.read` for the focused row, and `Script.agents` for the machines that may run it. Machine names come from `Agent.list`.
- 🔷 `New` and `Edit` apply to `scripts/` only. A clone is read-only. [7.0](7.0-tasks.md).
- 🔷 `New` calls `Script.create`. `Edit` calls `Script.update`. A save commits.
- 🔷 `Pull` calls `ScriptRepository.pull` on the selected clone and replaces the grid with the reply.
- 🔷 `Clone` calls `ScriptRepository.clone`. `Remove library` calls `ScriptRepository.remove` for that clone.
- 🔷 There is no delete-script call. A file under `scripts/` stays until a later plan says otherwise.
- 🔷 `Enable` ticks machines and calls `Script.enable` for each new pair. Clearing a tick calls `Script.disable`.
- 🔷 The header tick on the script grid selects every script in the current library. Enable then applies the same machines to each ticked script.

```
+--------------------------------------------------+

+--------------------------------------------------+
| [x]  path                      filetype          |

| 1 selected              [ Edit ] [ Enable ]      |
+--------------------------------------------------+

| #!/bin/sh                                        |
| apt-get update -y                                |
| machines   web-01, web-03                        |
+--------------------------------------------------+
```

## Assets — Software

- 🔷 One row per program, across the office. Not one row per machine.
- 🔷 The count and the versions are the audit.
- 🔷 Filters sit in the title action bar: operating system, name, behind, sign-off, group.
- 🔷 The data view shows the sign-off, the groups, the versions, and the machines that have this program.
- 🔷 A machine in that view opens the machine dialogue.
- 🔷 `Remove` creates a task that takes this program off the selected machines.
- 🔷 A program can sit in many groups. A group name is free text. Suggestions are names already used.
- 🔷 Sign-off is separate from groups. It has two levels.
  - Permitted. Signed off as okay.
  - Restricted. Signed off, and only some people should have it.
- 🔷 A program with no sign-off is the list to flag. Permitted is not a group name, and neither is Restricted.
- 🔷 The grid action bar sets that level on every ticked program: Permitted, Restricted, or Clear.
- 🔷 `Group` adds one typed name to every ticked program. Groups already on those programs stay.
- 💩 Who may have a restricted program. The level is enough for the list and the bulk action. The people themselves are a later plan.
- ℹ️ The catalog in [3.0 Later](3.0-server.md) may later feed group suggestions. The sign-off stays on the program.

## How an update is modeled

- 🔷 Debian already has the update. It is the package manager, on the machine.
- 🔷 The asset is the machine. Filter Machines to the ones that need updating. The header tick selects that whole filter. `Update` on the grid action bar runs the package manager on each ticked machine.
- 🔷 That click creates one task and one target per machine, then opens Running.
- 🔷 A program row can still say it is behind. That is the audit. It is handy. It is not the button that updates a Debian box.
- 🔷 Filtering Software by operating system and by "behind" stays, for the picture of what is stale.
- 💩 How a machine becomes "needs updating": the last inventory said the package manager has work, or a probe said so. The column is a later plan.
- 💩 Other systems update one program at a time. This flow is the Linux-server aim. A per-program update button waits until one of those systems is in scope.

```
Machines
title bar: OS = Debian, needs updating = yes
header tick: every row in that filter
grid action bar: [ Update ]
        |
        v
one task
  web-01  running
  web-03  queued
        |
        v
Tasks / Running
```

## Aim flows

Each aim in [1.0](1.0-aims.md), as a path through the pages.

### Audit the office

- 🔷 Open Software. The list is the office picture: one program, how many machines, which versions.
- 🔷 Filter to a name, or to an operating system, or to behind.
- 🔷 The data view is the versions, the sign-off, the groups, then the machines.
- 🔷 Open a machine only after that picture says which box.

```
Software
  nginx     12 machines    1.18 and 1.22    permitted    web
        |
        +-- data view: web-01 is the 1.18
                |
                +-- open web-01 dialogue
```

- 🔷 Nothing is installed or removed on this path.

### Keep Linux servers up to date

- 🔷 Dashboard shows the count of machines that need a package-manager update.
- 🔷 Open it. Machines is filtered: Debian, needs updating.
- 🔷 The header tick selects that filter. Clear a tick on a box that should wait.
- 🔷 `Update` on the grid action bar. The dialogue names the script and the machines. Save as draft, or approve now.
- 🔷 Running shows each machine. The data view is the package-manager output.
- 🔷 Software "behind" is a check before or after. It does not replace this path.

```
Dashboard
  4 machines need a package-manager update
        |
        v
Machines
  title bar: OS = Debian, needs updating = yes
  header tick
  grid action bar: [ Update ]
        |
        v
dialogue: package-manager update on web-01, web-03, ...
  [ Approve ]
        |
        v
Tasks / Running
  web-01 running    Reading package lists...
  web-03 queued
```

### Remove software that should not be there

- 🔷 The audit, or Monitoring "Not permitted", shows the program.
- 🔷 Tick the programs. `Remove` on the grid action bar.
- 🔷 One task, one target per selected machine. Running shows the uninstall output.
- 🔷 The person does not go to the desk.

```
Software
  header tick on the not-permitted filter
  ChatGPT, Steam
        |
        +-- grid action bar: [ Remove ]
                |
                v
        Tasks / Running
          desk-12 running
```

### Notice what should not be happening

- 🔷 A new program lands on the dashboard and on Monitoring "Not permitted".
- 🔷 Tick the rows. The data view shows the machine and the time.
- 🔷 `Permitted` when the office may have it. `Restricted` when only some people may have it. `Group` to file it under a free-text name. `Remove` when it should go. Remove follows the path above.
- 🔷 A new executable, or a socket this kind of machine should not have, is the same open-then-decide path once those events exist.

```
Dashboard
  desk-12  ChatGPT installed
        |
        v
Monitoring / Not permitted
  [x] ChatGPT   desk-12   today
        |
        +-- [ Permitted ]    row leaves this list
        +-- [ Restricted ]   row leaves this list, level is restricted
        +-- [ Group ]        adds a name, sign-off unchanged
        +-- [ Remove ]       --> Tasks / Running
```

### Do the same work on many machines at once

- 🔷 Every work button on the grid action bar takes the ticked rows.
- 🔷 The header tick is how a whole filter becomes that selection. Update all is that tick, then `Update`.
- 🔷 `Update` on many machines is one task.
- 🔷 `Remove` on many programs is one task.
- 🔷 `Permitted`, `Restricted`, and `Group` apply to every ticked program.
- 🔷 `New` on Tasks is the same shape for a script that is not an update or a remove.
- 🔷 Running is one row per machine, so a failure is a single box and the others keep going.

```
title bar: the filter
header tick: every row in it
grid action bar: one button
        |
        v
one task, or one sign-off, on
  web-01
  web-03
  web-04
```
