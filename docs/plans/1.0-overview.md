## Purpose

- 🔷 Remote management of machines.
- 🔷 An agent runs on each managed machine.
- 🔷 Argus is the control server.
- 🔷 A controller talks to Argus.
- 🔷 Phase 1 proves one desktop can be enrolled and then managed.
- 🔷 This file is the product. Implementation plans start at [2.0](2.0-agent.md).

---

## Directories

- 🔷 Four trees: `agent/`, `controller/`, `server/`, and `shared/`.
- 🔷 Source for each program lives in that directory.
- 🔷 `server/` is Argus.
- 🔷 `controller/` starts as the command-line client.
- 🔷 `agent/` is the cross-platform agent.
- 🔷 `shared/` is the code the agent and the controller both use. Namespace `Argus.Shared`.

---

## Roles

- 🔷 **Agent**
  - One cross-platform program.
  - Linux runs it under systemd.
  - Windows runs it as a service.
  - Installed as admin.
  - Thin.
  - Waits for a broadcast, then registers with certificates.
  - ℹ️ Implementation is [2.0](2.0-agent.md).
- 🔷 **Argus**
  - Issues certificates.
  - Distributes files.
  - Holds the machine records.
  - Publishes a short Avahi broadcast when a controller asks.
  - Avahi runs only on Argus. Clients browse.
- 🔷 **Controller**
  - Talks to Argus.
  - The basic controller is the command-line client. That is the one to start with.
  - It enrolls on the same broadcast and is stored as a control client.
  - It does not install an agent.
  - It is usually a Linux box. It can be a Windows box.
  - The first thing it can do is open the registration window.
  - The long-run client is a desktop application.
  - A web app is not the path under consideration.
  - The phone comes later, for registration at the machine and for alerts.

---

## Sockets

- 🔷 The main socket is the app RPC.
  - Registration, commands, identity, and warnings stay here.
- 🔷 A second socket carries downloads and other bulk transfer.
  - The osquery installer.
  - Later package file sets.
- 🔷 A transfer on the second socket must not clog the main socket.
- 🔷 The second socket is fixed in the Argus config.
- 🔷 The registration response sends that socket info to the client.

## Enrollment

- 🔷 The controller command-line client tells Argus to broadcast for a short time.
- 🔷 The controller shows a number.
- 🔷 The agent is already installed and is browsing.
- 🔷 The person types the number into the desktop.
- 🔷 The service does not open that window. Session 0 has no desktop.
- 🔷 Windows is [2.5](2.0-agent.md). `argus-prompt.exe` is the window and the tray. Install opens the window. Closing it leaves the tray. The tray shows the window again and starts at sign-in. A normal user cannot quit or uninstall it. The only action is register, and only when this machine has no certificate. Once registered, the tray says ''Connected to management server'' or ''Disconnected''. While disconnected, the agent retries every two minutes. The prompt sends the number to the service on a local pipe.
- 🔷 Linux is [2.6](2.0-agent.md). No GNOME Shell extension and no tray. The application menu runs `argus-prompt --register`.
- ℹ️ GDBus exists on Windows. A sign-in bus is not visible to the service, so D-Bus between them means running `dbus-daemon` as well. The Windows pipe does not.
- 🔷 The agent registers only while that window is open.
- 🔷 Registration uses the RPC library and certificates, the same way as the other projects.
- 🔷 A managed agent is stored as a machine. A controller is stored as a control client.
- 🔷 The record starts pending, or in process.
- 🔷 The registration response includes the download socket from the Argus config.
- 🔷 The agent downloads the osquery installer on that socket and installs it.
- 🔷 A basic query then fills the record.
- 🔷 The phone does the same window later.
  - Install the Android client.
  - Tell Argus to broadcast.
  - The phone shows the number.
  - Type it into the desktop.
- ℹ️ OLLMchat pairing: `libocrpc/Transport/PairPublish.vala`, `ollmfilesd/ClientCert.vala`.
- ℹ️ OLLMchat shows a six-digit PIN and keeps the window near 60 seconds.
- 💩 Use that length and that number of digits. Confirm before build.

## Machine record

- 🔷 Server records follow osquery’s data to a large degree.
- 🔷 First data is only identity.
  - Username.
  - Computer name.
  - Type of computer.
  - Speed.
  - An identifier that can be referenced.
  - Some network information.
- 💩 Read those fields from osquery `system_info`, the logged-in user, and the interface addresses. Confirm the tables before build.

## Software

- 🔷 After identity, the agent collects the installed programs and Argus stores them against the machine.
- 🔷 An online catalog categorises known software. It may be a git repository.
- 🔷 A catalog entry knows a package well enough to categorise it.
- 🔷 A controller can see which catalog packages a machine does not have.
- 💩 Use the osquery programs table on Windows. Confirm before build.
- 💩 Where the git repository lives, and the file layout inside it. Confirm before build.

## Install and uninstall

- 🔷 A controller can add a catalog package to a machine that does not have it.
- 🔷 Install is a download, then an install.
- 🔷 Argus stores the files and can fetch them from an online source.
- 🔷 The agent downloads the file set on the download socket and runs the install, including any install script.
- 🔷 A package that should not be on the machine can be removed quickly.
- 🔷 Argus tells the agent which installed package to remove.
- 🔷 The agent runs that package’s Windows uninstall. Windows uninstall is vaguely standardised.
- ℹ️ The usual entries are `QuietUninstallString` and `UninstallString` under the uninstall registry key.
- 💩 Prefer the quiet string when it is present. Confirm before build.
- 💩 How much disk the file store gets, and whether a fetch is a Pman process. Confirm before build.

## Monitoring

- 🔷 The agent notices a new or removed program and tells Argus.
- 🔷 Argus raises a warning a controller can see.
- 🔷 The critical case is a staff member installing a ChatGPT desktop client. That warns quickly.
- 🔷 A cron or shell script asks Argus whether any warning is open, so Nagios can show it.
- 🔷 The same warning can go to Android phones that have the app.
- 🔷 Later: warn when a port in use is not the expected one. That is osquery data.
- ℹ️ Existing Nagios check scripts: `server.media-outreach/etc/nagios/`.
- 💩 How often the agent compares the program list. Confirm before build.
- 💩 Argus is queried by that script. It is not itself a Nagios plugin host. Confirm before build.

## Packaging

- 🔷 A clean Debian install, and a Windows setup program.
- 🔷 GitHub Actions builds both, the same way OLLMchat does.
- 🔷 The Debian package installs the program and, for a service, its systemd unit.
- 🔷 The Windows build is a setup exe. It installs under Program Files as administrator, the way `app.Snappr2/packaging/windows/snappr.nsi` does, and it registers the agent service.
- 🔷 OLLMchat’s installer is per-user under LocalAppData. That is the wrong install for this agent.
- 🔷 The agent ships both. The server ships the Debian package. The controller command-line client ships both when that plan starts.
- ℹ️ OLLMchat Debian: `.github/workflows/x-debian.yml`, started by `release-debian.yml`. `dpkg-buildpackage` on Ubuntu.
- ℹ️ OLLMchat Windows: `.github/workflows/x-windows.yml`, started by `release-windows.yml`. MSYS2 on `windows-latest`, then NSIS. Artifact is `OLLMchat-*-Setup.exe`.
- ℹ️ Snappr also ships an NSIS setup exe, built on a Windows machine over SSH. That host is not the build we copy. The GitHub job is the OLLMchat one.
- 💩 One package per program, not OLLMchat’s split library set. Confirm before the first Debian packaging.
