## Purpose

- 🔷 How installed software stays in sync. Debian packages, RPM packages, and Windows programs.
- 🔷 Two phases. Phase 1 is the columns and the startup sync. Phase 2 is the package monitors.
- ✔️ The startup snapshot is applied as a differential update.
- ℹ️ The list is [5.9](5.9-assets-software.md). Filters are [5.9.2](5.9.2-assets-software-filters.md). The machine grid is [5.9.3](5.9.3-assets-software-machines.md). Enrichment is [5.10](5.10-data-enrichment.md).
- ℹ️ Column names are [4.0](4.0-data-types.md).

---

## Phases

- 🔷 ✔️ Phase 1. The standard columns, and the standard sync. `added_dt`, `updated_dt`, and `deleted_dt` on every table. The startup snapshot writes them. The package list reads them.
- 🔷 Phase 2. The package monitors. One Linux class and one Windows class. Debian, RPM, and Windows each have a monitor.

---

## Phase 1 ✔️

The standard columns, and the standard sync. The startup snapshot writes `added_dt`, `updated_dt`, and `deleted_dt`. The package list reads them.

### Startup snapshot

- 🔷 The agent queries `deb_packages`, `rpm_packages`, and `programs` once at startup and calls `OSQuery.sync`. This host sends about seven thousand Debian rows.
- ℹ️ Android does not query. A database copy after reboot held 7051 `deb_packages` rows for that agent.
- ✔️ The server applies that set as a differential update. `shared/OSQuery/Row.vala` `sync_rows`.
  - A stored row that differs is updated.
  - A new row is inserted.
  - A stored row the snapshot left out is deleted.
  - The table is not wiped and filled again.
- 🔷 ✔️ The apply writes `added_dt`, `updated_dt`, and `deleted_dt`.
- 🔷 ✔️ The names end in `_dt`. That marks a datetime. Column names are [4.0](4.0-data-types.md).
- 🔷 ✔️ Every table has the three columns. `agent`, the osquery tables, and the task tables.
- 🔷 ✔️ They are properties on `OSQuery.Row`. `sync_rows` sets them. It does not test whether the table has the columns.
  - An insert sets `added_dt`.
  - A stored row whose columns change sets `updated_dt`.
  - A row the snapshot left out stays, and `deleted_dt` is set. That replaces the delete `sync_rows` does today.
- 🔷 ✔️ Phase 1 uses them on the package sync. Other tables carry the columns. A table that syncs through `sync_rows` gets the same writes. A table that does not sync leaves them at `0`.
- 🔷 ✔️ Each value is a unix time, `INTEGER`. `0` means that has not happened.
- 🔷 ✔️ A row that comes back after `deleted_dt` clears `deleted_dt` and sets `updated_dt`.
- 💩 ✔️ `compare` skips the three columns. The snapshot does not send them. A stored time against `0` would mark the row changed.
- ℹ️ An install time is kept when osquery already sends one. `rpm_packages.install_time` is a unix time. `programs.install_date` is text. `deb_packages` has no install time. No install column is added. A new package is found by `added_dt`.

### Controller load

- 🔷 ✔️ The default list leaves out a row whose `deleted_dt` is set.
- 🔷 ✔️ A later load passes a time. The reply is every row whose `added_dt`, `updated_dt`, or `deleted_dt` is after that time. Deleted rows are in that reply.
- ℹ️ `DebPackages.list`, `RpmPackages.list`, and `Programs.list` take `ii`: `agent_id`, `since`. [rpc-commands](../rpc-commands.md).
- ℹ️ The stores still apply a full list with a client hash map. That code stays until this load exists.

## Phase 2

After the startup snapshot, a monitor watches for package changes. The agent keeps that fetch. The monitor sends the rows that changed, and the rows that left with `deleted_dt` set.

- 🔷 ⏳ Linux is one class. Windows is one class. Both are `Argus.Agent.PackageMonitor`.
  - 🔷 `agent/linux/PackageMonitor.vala` and `agent/Win32/PackageMonitor.vala`. Meson compiles one of them. The same split as `Argus.Agent.Command`.
- 🔷 ⏳ The Linux class has `debian()` and `rpm()`. Startup `os_version` chooses one. `platform` or `platform_like` of `debian` calls `debian`. `rhel` calls `rpm`.
- 🚫 The monitor does not query osquery to decide the OS, and it does not test which database directory exists.
- 🔷 ⏳ The Windows class runs the Windows monitor.
- 🚫 Android has no monitor.
- 🔷 ✔️ The startup fetch of `deb_packages`, `rpm_packages`, and `programs` stays on the agent. `Application.package_rows`.
- 🔷 ✔️ The monitor send is `OSQuery.update`. It carries the new rows, the changed rows, and the rows that left with `deleted_dt` set.
- 🔷 ✔️ `OSQuery.update` applies only those rows. A row with `deleted_dt` set is a removal. A row left out stays. `OSQuery.sync` stays the full startup snapshot.
- ℹ️ The update columns are [5.10](5.10-data-enrichment.md). This section is the installed rows.

### Debian

- 🔷 inotify on `/var/lib/dpkg`. A change arms a deferred rescan. The rescan queries `deb_packages` and sends the difference.
- 💩 The rescan waits until a non-blocking fcntl write lock succeeds on `/var/lib/dpkg/lock` and `/var/lib/dpkg/lock-frontend`. A quiet timer fires during a long maintainer script. `flock` does not see dpkg's lock.
- ℹ️ Watched on the GNOME guest `ubuntu2604`, 2026-11-12. dpkg writes each step under `/var/lib/dpkg/updates/` and then renames `status-new` onto `status`.
  - `apt-get install hello` journalled `install ok unpacked`, then `install ok installed`, then renamed `status`. A second rename followed for the triggers. The frontend lock closed after that.
  - `apt-get remove hello` renamed `status` three times. The package was already absent at the first rename. The later renames were the triggers.
  - `hello` has no conffiles, so remove drops the row. A package with a conffile stays, status `deinstall ok config-files`, until purge.

### RPM

- 🔷 inotify on `/var/lib/rpm`. A change arms a deferred rescan. The rescan queries `rpm_packages` and sends the difference.
- 💩 The rescan waits until a non-blocking fcntl write lock succeeds on `/var/lib/rpm/.rpm.lock`. That is rpm's transaction lock. This was not watched on a machine.
- ℹ️ The database may live at `/usr/lib/sysimage/rpm`, with `/var/lib/rpm` linked to it. The watch is the directory that holds `.rpm.lock`.

### Windows

- 🔷 The class subscribes to the Application log. The source is `MsiInstaller`. Install is event `1033` and `11707`. Removal is `1034` and `11724`. The class then sends the `programs` difference.
- ℹ️ An exe install or a store install does not emit `MsiInstaller`. The startup snapshot still has those programs.
- ℹ️ The event is the signal. The program row comes from `programs`.

## LLM notes

- 🚫 Do not build the Software list here. That is [5.9](5.9-assets-software.md).
- 🚫 Do not build the filters here. That is [5.9.2](5.9.2-assets-software-filters.md).
- 🚫 Do not build the machine grid here. That is [5.9.3](5.9.3-assets-software-machines.md).
- 🚫 Do not add `update_available`. That is [5.10](5.10-data-enrichment.md).
- 🚫 Do not add an install-time column. A new package is `added_dt`.
- 🚫 Do not wipe a package table and insert the snapshot again.
- 🚫 Do not drop a row the snapshot left out. Set `deleted_dt`. The since query returns that row.
- 🚫 Do not put the three columns only on the package tables. Every table has them.
- 🚫 Do not test whether a table has `added_dt`, `updated_dt`, or `deleted_dt`.
- 🚫 Do not send a partial package list through `OSQuery.sync`. A row left out of that full set is marked deleted. The monitor difference goes through `OSQuery.update`.
- 🚫 Do not install or run `osqueryd`. The package query stays `osqueryi`. The watch is the monitor class.
- 🚫 Do not watch packages by polling. Debian and RPM use inotify. Windows uses the Application log. The package query runs when the monitor fires.
- 🚫 Do not treat a `status` rename as the end of the install. One apt run checkpoints more than once.
- 🚫 Do not send an inotify event or a log event as a package row.
- 🚫 Do not add a base class over the Linux and Windows monitors.
- 🚫 Do not wrap both monitors in one class with ifdefs.
- 🚫 Do not walk the full lists in the controller stores to find the difference. The agent compares its stored fetch with the new query.
- 🚫 Do not extend the client hash-map diff in the stores.
