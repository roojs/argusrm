## Purpose

- 🔷 Build the generic agent in `agent/`.
- 🔷 One program, run on each platform.
- 🔷 Four phases for the agent, then the desktop registration flow: the source tree, registration, the Windows tray, the Linux application, osquery and the identity post, then notification and remote command execution.
- ℹ️ The call list is [RPC commands](../rpc-commands.md).
- ℹ️ The Debian unit file and the NSIS installer are [1.0 Packaging](1.0-overview.md). The Windows service calls live in this program.
- ℹ️ Software list, install, uninstall, and warnings stay in [1.0](1.0-overview.md) until a later plan.

## Where the code comes from

- 🔷 Link `libocrpc`. Do not copy the library into this tree.
- 🔷 The registration client to adapt is `OLLMchat.Settings.FilesdClient.try_connection` in `libollmchat/Settings/FilesdClient.vala`.
  - It builds a TLS connection, sends `ClientCert.request_registration`, and stores `client.pem` and the CA.
  - The certificate files come from `OLLMrpc.Transport.Cert` in `libocrpc/Transport/Cert.vala`.
- 🔷 `ollmfilesd/ClientCert.vala` is the server side of that call. It stays on the server.
- 🔷 Avahi publish stays on the server. The pattern is `libocrpc/Transport/PairPublish.vala`.
- 🔷 Linux browse can use the Avahi client library OLLMchat already links for publish. There is no desktop browse class to copy.
- 🔷 The phone browse is `shared/android/PairBrowse.java`, copied from OLLMchat `android/PairBrowse.java`. The Android controller uses that class. `shared/android/Browse.vala` is `Argus.Shared.Browse` on Android and calls it.
- 🔷 The registration window is `shared/RegisterWindow.vala`, from OLLMchat `ollmapp/android/FileConnectionAdd.vala`. One dialog for the agent and the controller. The sixth digit runs the check. OLLMchat does not.
- 🔷 From Snappr, take the Windows admin install, not the application.
  - `packaging/windows/snappr.nsi` installs to Program Files as administrator and stops the running program before replacing it.
  - `scripts/copy-exe-runtime-dlls.sh` puts the GLib DLLs beside the exe. OLLMchat has the same script.
- 🔷 Snappr stays up with a logon scheduled task and `src/Win32/TrayKeeper.vala`. That is a separate tray process. This agent is one executable. `argus-agent` is the service. `argus-tray` is the window and the icon, in `agent/Win32/tray/`.
- 🔷 A Windows service handler is not in Snappr or OLLMchat. Snappr’s tray plan records that a service was the wrong model for a WebView. The service has no window, so the handler is new code.
- ℹ️ Snappr `src/Win32/win32.vapi` is the tray, the menu, and `CreateProcessW`. The service calls and the tray calls are both `agent/Win32/win32.vapi`. The tray, process, and pipe symbols are copied from that Snappr vapi. `CreateProcessAsUserW` and the session token calls are the service launch. `agent/Win32/win32.h` has Snappr's includes plus `wtsapi32.h`.
- ℹ️ Snappr `src/main.vala` sets GTK, fontconfig, and WebView paths. This program does not link those.
- 🔷 Windows browse is the same discovery as OLLMchat `android/PairBrowse.java`. Service `_rpc._tcp`, TXT `id`, then host and port. `poll` returns the id, a newline, and `host:port`. Windows 10 does that with `DnsServiceBrowse` and `DnsServiceResolve` in `dnsapi`. The query name is `_rpc._tcp.local`. That is not a different service type. OLLMchat has no Win32 browse to copy.

## Phase 1 — codebase

- 🔷 `✔️` A Meson project in `agent/` that builds one executable and runs on Linux. The Windows service files are in the tree and are compiled only on Windows.
- 🔷 `✔️` No broadcast, no registration, and no osquery in this phase.
- 🔷 `✔️` Top-level `meson.build` is the project. `build/` is that directory, not a subdirectory of `agent/`. `agent/meson.build` builds `argus-agent`. Depends on `glib-2.0`, `gobject-2.0`, and `gio-2.0` (`GLib.Application` is Gio). Windows also links `advapi32`, `user32`, `shell32`, `psapi`, and `wtsapi32`.
- 🔷 `✔️` `agent/namespace.vala` — `namespace Argus.Agent`. Same role as `ollmfilesd/namespace.vala`.
- 🔷 `✔️` `agent/Application.vala` — `Argus.Agent.Application`, a `GLib.Application`.
  - `main` is at the bottom of this file, as in `ollmfilesd/Application.vala`.
  - Flags are `HANDLES_COMMAND_LINE` and `NON_UNIQUE`. `command_line` parses `OptionEntry` values, including `--debug` and `--debug-critical`. Properties are `host`, `port`, and `pin`. `hold` keeps the process up. Service mode is not used: it rejects arguments.
  - On Windows, `main` reads the basename of `args[0]` first. `argus-tray` runs `Argus.Agent.Win32.Tray`. `argus-agent` constructs `Argus.Agent.Win32.Service` and calls `start`. A console launch runs `Argus.Agent.Application` directly.
- 🔷 `✔️` `agent/Win32/win32.vapi` — `namespace Argus.Agent.Win32`. Service control calls only. `StartServiceCtrlDispatcherW`, `RegisterServiceCtrlHandlerW`, `SetServiceStatus`.
- 🔷 `✔️` `agent/Win32/Service.vala` — `Argus.Agent.Win32.Service`. `start`, `service_main`, and `control` are instance methods. `service_main` starts `Argus.Agent.Application`. The dispatcher function pointers have no instance argument, so they call back into the `Service` that `start` registered.
- ℹ️ Linux needs no extra class. systemd runs the same executable. The unit file is packaging.
- ℹ️ `agent/` stays the directory from [1.0](1.0-overview.md). No `src/` under it.

## Phase 2 — register

- 🔷 `✔️` Browse and register are shared by the agent and the controller.
- 🔷 `✔️` `shared/namespace.vala` — `namespace Argus.Shared`.
- 🔷 `✔️` `shared/Browse.vala` — Linux `Argus.Shared.Browse`. Avahi service `_rpc._tcp`, TXT `id`, then host and port.
- 🔷 `✔️` `shared/windows/Browse.vala` — the same class on Windows. `DnsServiceBrowse` for `_rpc._tcp.local`, then `DnsServiceResolve` for the IPv4 address and TXT `id`. Same poll line.
- 🔷 `✔️` `shared/android/PairBrowse.java` — phone browse copied from OLLMchat. Service `_rpc._tcp`, TXT `id`, then host and port. `poll` returns the id, a newline, and `host:port`. The Android controller binds this class.
- 🔷 `✔️` `shared/android/Browse.vala` — `Argus.Shared.Browse` when the host is Android. `start`, `poll`, and `stop` call `PairBrowse`. `label` is the phone name from that bind, passed as the registration requester.
- 🔷 `✔️` `shared/Register.vala` — `Argus.Shared.Register.try_connection`. The registration half of `FilesdClient.try_connection`: TLS, `ClientCert.request_registration`, `OLLMrpc.Transport.Cert` under the user data directory `argus/`.
  - Reply `retval` is a string array. Index 0 is the client certificate PEM. Index 1 is the CA PEM. Index 2 is the download socket `host:port`, also written as `download` next to the certificates. Index 3 is the download URL path, including the extension, also written as `download-path`. Later entries are listen addresses.
  - The call arguments are the pin, the certificate request, the requester, and the OS family. Windows sends `windows`. Android sends `android`. Linux reads `/etc/os-release` before the call. Debian and Ubuntu send `debian`. Fedora, RHEL, CentOS, and SUSE send `rpm`. When that file does not decide, `dpkg` on `PATH` sends `debian` and `rpm` on `PATH` sends `rpm`. The server chooses the URL path from that family.
  - 💩 `✔️` `GLib.Environment.get_os_info` reads `ID` and `ID_LIKE`. The file is not split by line.
- 🔷 `✔️` After install it browses for the Argus broadcast. With no host and port, the process calls `Browse.start`. `--pin` alone registers when a browse line arrives. `--host`, `--port`, and `--pin` together still register immediately.
- 🔷 `✔️` `--host`, `--port`, and `--pin` are `OptionEntry` values copied onto the `host`, `port`, and `pin` properties. `--pin` is the number from the window. `--debug` shows the log on stderr.
- 🔷 `✔️` The call sends that pin. The server accepts it only while the window is open.
- 🔷 `⏳` A public Debian server stays locked down. Argus records the client IP, opens iptables for that IP while it broadcasts, then locks down again. See [1.0 Public servers](1.0-overview.md). That work is [3.0](3.0-server.md).
- 🔷 `✔️` It uses the OLLMchat certificate call over the installed `libocrpc` (`--pkg ocrpc`, `-locrpc`).
- 🔷 `⏳` Argus stores it as a machine, pending or in process. That store is [3.0](3.0-server.md).
- 🔷 `✔️` The client reads the download socket from index 2 of the registration reply, and the URL path from index 3.

## Phase 2.5 — Windows tray and registration

- 🔷 `✔️` One built executable. The installer also writes it as `argus-tray.exe`. `main` reads the basename of `args[0]` first. `argus-tray.exe` runs `Argus.Agent.Win32.Tray` (`agent/Win32/tray/`). `argus-agent.exe` is the service.
- 🔷 `✔️` The tray icon is Snappr's sequence: message window, `Shell_NotifyIconW` with `NIM_ADD`, `NIM_SETVERSION` (`NOTIFYICON_VERSION_4`), and `NIM_MODIFY`. The tip starts as ''Register'' via `copy_wide`. Left click uses the same `NIN_SELECT` / `WM_LBUTTONUP` timer. There is no quit menu. Snappr's second process is not copied. `set_tip` is Snappr's.
- 🔷 `✔️` The registration window is `shared/RegisterWindow.vala`, one class for Android, Linux, and Windows. It is the OLLMchat `FileConnectionAdd` dialog. The agent and the controller both use it. The sixth digit calls `Argus.Shared.Register`. OLLMchat waits for the Request button.
- 🔷 `✔️` When `argus-tray` starts, it presents the registration window. Install opens it by starting the tray. Clicking the tray icon presents that window. Closing it leaves the tray. If this machine is already registered, there is no action and the window is not presented.
- 🔷 `✔️` A normal user cannot quit or uninstall. The tray has no quit menu and no uninstall action. Uninstall is the administrator setup. The service starts `argus-tray` when a user is signed in. There is no third process.
- 🔷 `✔️` Once registered, the service sets the tray text to ''Connected to management server'' or ''Disconnected'' with Snappr's `tip ` message and `set_tip`. While disconnected, the service connects to the stored download socket every two minutes and updates that text.
- 🔷 `✔️` The service starts `argus-tray.exe` with `CreateProcessAsUserW`
  when that process is not already running. The check is Snappr's process
  scan. The tray writes the six digits to `\\.\pipe\Argus.Register`. The
  service calls `Argus.Shared.Register`. Android calls `Register` in the
  window. Linux registration is proposed separately in phase 2.6.
- 🔷 `✔️` The tray does not elevate. The pipe rejects remote clients and grants read/write access to authenticated local users; the `LocalSystem` service performs registration and stores the certificate. A machine that already has a certificate cannot replace it through the pipe.
- ℹ️ GDBus is in GLib on Windows. Windows does not run a session bus, and a bus started at sign-in is not visible to Session 0. A bus both processes can open means shipping `dbus-daemon` as well. The pipe does not add that process.

The window sends `Browse.label` as the requester. `shared/android/ArgusApplication.java` binds `PairBrowse` the way OLLMchat's `OllmApplication` does, and loads `argus-agent`.

## Phase 3 — osquery and identity

- 🔷 `✔️` It downloads the Windows osquery installer on the download socket.
- 🔷 `✔️` Linux downloads that installer on the same socket and installs it. Osquery is not in the distro archive.
- 🔷 `✔️` That transfer stays off the main app socket.
- 🔷 `✔️` It installs osquery.
- 🔷 `✔️` It runs a basic query and posts the identity fields from [1.0](1.0-overview.md).
- 🔷 `✔️` Argus fills the machine record from that post. The `agent` row is the machine. The osquery tables point at it. See [3.0 Phase 3](3.0-server.md).
- 💩 `✔️` The identity post is bin RPC, same as registration, with the client certificate from `argus/`.
- 💩 `✔️` The app socket is the host and port `try_connection` used. `shared/Register.vala` writes that as `server`. The identity post uses it.
- 🔷 `✔️` The download socket only listens for download requests. The fetch is a standard HTTP GET over TLS, authenticated with the client certificate. The server allows or refuses that certificate.
- 🚫 `Download.get` is not the download API.
- ℹ️ `OLLMrpc.Transport.HttpClient` posts an RPC body. It is not this GET.
- 🔷 `✔️` `agent/Download.vala` sends `GET https://` plus the `download` host and port and the URL path. The saved basename is that path's last segment: `osquery.msi`, `osquery.exe`, `osquery.deb`, or `osquery.rpm`.
- 🔷 `✔️` Osquery rows are objects. A column is stored on the property of that name. Values are not renamed.
- 🔷 `✔️` `osqueryi --json`. The line-oriented stdout is not parsed.
- 🔷 `✔️` The row objects live in `shared/OSQuery/`, namespace `Argus.Shared.OSQuery`. The server and the agent use the same types.
- 🔷 `✔️` Those objects are `Json.Serializable`. `Query<T>.select` fills each row with `Json.gobject_deserialize`.
- 🔷 `✔️` Numeric columns are `int`. `int64` is only for a value that does not fit in `int`.
- 💩 `✔️` `physical_memory` is the `int64`. The other numeric columns are `int`.
- 💩 `✔️` The column `type` is the property `ctype`, because Vala rejects a property named `type`.
- 💩 `✔️` `agent/OSQuery/Query.vala` is `Argus.Agent.OSQuery.Query`. It runs `osqueryi --json` and fills the shared row objects.
- 🔷 `✔️` `OSQuery.sync` sends one table. The arguments are the table name and the array of row objects. Each result set is its own call. The client certificate is the machine.
- 🔷 `✔️` `agent/Download.vala` — `Argus.Agent.Download.fetch`. Writes the GET body under the temp directory. `path` is that file.
- 🔷 `✔️` `Register.try_connection` calls `OLLMrpc.Transport.TlsClient`. The identity post sends on the app socket the process already opened.
- 💩 `✔️` Registration sets `accept_any`. `Application.open_link` sets `accept_any` and the client certificate. The certificate load is not in `OSQuery.Initialize`. The HTTP GET presents that same client certificate.
- 💩 `✔️` `agent/OSQuery/Initialize.vala` — `Argus.Agent.OSQuery.Initialize.start` runs `run` on a thread. `running` stops a second start while that thread is in `run`.
  - When `osqueryi` is missing: read `download-path` and `fetch` that path. Windows runs `msiexec.exe /i <path> /qn` for `.msi`, otherwise `<path> /S`. Linux runs `dpkg -i <path>` for `.deb`, or `rpm -U <path>` for `.rpm`.
  - Then `osqueryi --json` into `Argus.Shared.OSQuery` rows, then those rows are posted.
- 🔷 `✔️` Android has a dummy initialization, so we can pretend it supports initialization. `start` does not install or query.
- 💩 `✔️` `agent/android/OSQuery/Initialize.vala` is `Argus.Agent.OSQuery.Initialize`. The Android build compiles that file instead of `agent/OSQuery/Initialize.vala`.
- 🔷 `⏳` A real Android initialization might mean bundling the library in the Android build.
- ℹ️ The osquery row objects are already in `argus-shared`. The Android agent links that library. The dummy is only the agent `Initialize`.
- 💩 `✔️` Start after a successful registration, and when a process that
  already has `client.pem` stays up. That is `Application.command_line`,
  and `Win32.Service.tick`.

## Phase 4 — notification and remote execution

- 🔷 `⏳` This is the last phase. The server tells the connected agent to run a command. That tell is a notification, on that agent's connection.
- 🔷 `⏳` A notification is for one connection. There are two deliveries.
  - A broadcast notification goes to every connection.
  - A client notification goes to one connection.
  - This phase uses the client notification.
- 🚫 Signals, and `RPC-Live-Subscribe`, are not this phase. Bubble is not this phase.
- ℹ️ One `OLLMrpc.Notification` is both deliveries. `Connection.write` sends it to that connection. `Listen.broadcast` sends it to every connection. `libocrpc/Notification.vala`, `libocrpc/Transport/Connection.vala`, `libocrpc/Transport/Listen.vala`.
- ℹ️ The call fields are [RPC commands](../rpc-commands.md).
- 🔷 `⏳` The notification name says the agent receives it. That name is not the object.
- 🔷 `⏳` The object set on that notification is an Argus command. Down the wire it is called `Argus.Command`.
  - The identifier.
  - The command.
  - The environment variables.
  - The current working directory.
  - The same set has to run the command on Windows and on Linux.
- ℹ️ `g_spawn_async` takes `working_directory`, `argv`, and `envp`. `CreateProcess` takes `lpCurrentDirectory`, `lpCommandLine`, and `lpEnvironment`.
- 🔷 `⏳` On the server the object is `Argus.Server.Command`. The server makes it.
- 🔷 `⏳` On the agent the object is `Argus.Agent.Command`. The agent executes it.
- 🔷 `⏳` Those two classes do not have to be the same. The server command maps to the agent command.
- 🔷 `✔️` `Argus.Agent.Command` is a Linux class and a Windows class.
  - They monitor the sockets differently.
  - One class wrapped in ifdefs would be overwhelming.
- 🔷 `✔️` Android has a dummy command for the time being. Managing a phone is a remote possibility. How that run would work is not known.
- 🚫 A base class is not the split.
- 💩 `✔️` `agent/linux/Command.vala`, `agent/Win32/Command.vala`, and `agent/android/Command.vala` are all `Argus.Agent.Command`. Meson compiles one of them. Each registers the bin alias `Argus.Command`. The Android `run` does not spawn. It sends `Command.stdout` with an empty chunk.
  - `identifier`, `command`, `environment`, and `cwd` on both, in that order.
  - `environment` is `as`. Each entry is `NAME=value`.
  - `cwd` is the current working directory.
  - The notification `args` hold that one object.
  - Stdin, stdout, and stderr stay open.
  - Linux watches stdout and stderr with `IOChannel.add_watch`, the same read as a bubble command. Windows waits with `IOChannel.win32_poll`.
  - Linux runs the command string with `sh -c`. Windows runs it with `cmd.exe /c`.
  - An empty `cwd` or an empty `environment` inherits the agent process.
  - Stdout lines are `Command.stdout`. Stderr lines are `Command.stderr`. Each call is that chunk.

### Listen

- 🔷 `✔️` The connected agent watches the app socket for notifications.
- 🔷 `⏳` The command class deals with the command notifications.
- ℹ️ `OLLMrpc.Client` already takes a `Notification` off the stream, separate from a `Response`. `TlsClient.call` only waits for a `Response`. The listener reads notifications on the open app socket.
- 🔷 `✔️` Every notification has a method. The listener switches on it.
- 💩 `✔️` `Application.notification` switches on the method. `agent.run` hands an `Argus.Command` to `Argus.Agent.Command`. `agent.send` follows up on one. The Linux, Windows, or Android file for that class is chosen by the build. Any other method returns.
- 💩 `✔️` After `open_link`, the process connects `TlsClient.notification` and calls `TlsClient.watch`. [2.4-listen.md](2.4-listen.md).
- 🔷 `✔️` An `agent.send` notification carries an id so a later notification can follow up on a running command.
- 💩 `✔️` The id is the command `identifier` int. Arguments are `is`: identifier, then the text. `Command.send` writes that text to the command's stdin. Android logs and does not write. `Notification.id` is an int and is not this id.

- 🔷 `✔️` The agent sends `Command.stdout`. That is an RPC call, not a notification.
  - Each call is the next stdout chunk.
- 🔷 `✔️` The agent sends `Command.stderr`. That is an RPC call, not a notification.
  - Each call is the next stderr chunk.
- 💩 `✔️` Both arguments are identifier `i` and chunk `s`. `Command.run` sends them on the app socket.
- ℹ️ The file, the notification to the controller, and how the server learns that the process exited are the server. They are not an agent action. See [3.0 Phase 4](3.0-server.md) and [RPC commands](../rpc-commands.md).
