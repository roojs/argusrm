# 2.1 Registration flow

**Status:** ⏳ proposed

**Pointer:** `docs/guide-to-writing-plans.md` — **Checklist for plans**.
Proposed Vala must follow `docs/coding-standards.md`.

**Parent:** [2.0-agent.md](2.0-agent.md)

---

## Purpose

- 🔷 `⏳` Replace Linux `--register` with state-driven `argus-agent` startup.
- 🔷 `⏳` Run registration only in a root `argus-agent` process.
- 🔷 `⏳` Support desktop Polkit and headless root registration.
- 🔷 `⏳` Set up, restart, and verify systemd or SysV services.
- 🔷 `⏳` Keep first installation separate from service setup.
- ℹ️ Linux currently has no registration entry point.

---

## Required startup flow

- 🔷 `⏳` Plain `argus-agent` is the only public Linux entry point.
- 🔷 `⏳` A non-root desktop process only relaunches the same executable through Polkit.
  - It does not show registration UI.
  - It does not check the root service over D-Bus before elevation.
- 🔷 `⏳` A non-root process without a desktop exits with:
  `Run argus-agent as root.`
- 🔷 `⏳` Registration runs only inside the elevated or directly started root process.
- 🔷 `⏳` The root process checks service and registration state.
  - If the machine is registered and the service is running:
    - Report that the process is already running and exit.
  - If the service is not running, set it up and start it before continuing.
  - If the machine is not registered, continue to registration.
- 🔷 `⏳` A root desktop process shows the registration window.
- 🔷 `⏳` A root process without a desktop prompts for the registration PIN in the terminal.

---

## Registration and completion

- 🔷 `⏳` The PIN is entered only after the process is running as root.
- 🔷 `⏳` The PIN is absent from process arguments and logs.
- 🔷 `⏳` Registration writes the machine certificate to the system agent data directory.
- 🔷 `⏳` Existing complete machine certificates are not replaced.
- 🔷 `⏳` After receiving the certificate:
  - Restart the systemd agent, or the SysV/init.d agent when systemd is unavailable.
  - Query service status.
  - Query whether the service is connected to the management server.
  - Report both running and connected state in the registration UI.
- 🔷 `⏳` Keep a successful registration window open for about ten seconds before closing.

---

## Registration window

- 🔷 `⏳` Use a vertical, centred layout:
  - A light-weight `Enter registration PIN` heading.
  - A large PIN entry.
  - Registration status below the entry.
- 🔷 `⏳` Completing the PIN starts registration.
- 🔷 `⏳` Show progress, failure, and success in the status area.
- 🔷 `⏳` Use a custom header bar with only a close button.
- 🔷 `⏳` Closing the window cancels registration.

---

## Service status contract

- 🔷 `⏳` D-Bus is used only between the root registration process and the service for status.
- 🔷 `⏳` Running and connected-to-management-server are separate states.
- 🔷 `⏳` Registration, PIN transfer, and certificate writes do not use D-Bus.

---

## Installation and upgrades

- 🔷 `⏳` First installation installs files but does not register the machine.
- 🔷 `⏳` First installation does not enable or start the agent service.
- 🔷 `⏳` Registration performs initial service setup.
- 🔷 `⏳` Debian upgrades restart the systemd or SysV service only when it is already enabled.

## Shared requirements

- 🔷 `⏳` Keep Linux startup and service behavior in the Linux application subclass.
- 🔷 `⏳` Use configured installation and state paths rather than hard-coded directories.
- 🔷 `⏳` Keep the desktop and terminal flows behaviorally equivalent after elevation.
