## Purpose

- 🔷 Tasks are the core activity of Argus.
- 🔷 A task is a command on a machine, with more around it.
- 🔷 What actually runs is a script. Fixed, or generated.
- 🔷 Tasks live in the database.
- 🔷 Output stays on the filesystem we already have.
- 🔷 The server holds a library of standard scripts.
- 🔷 A script repository on this server feeds that library.
- ℹ️ `argus-controller --command` is the thin run we already have. [5.0](5.0-controller.md). It creates a task and the task runs it. [7.1](7.1-tasks-implementation.md).
- ℹ️ Column names lean on PMan / mtrack (`mtrack_action`, `mtrack_action_file`, `mtrack_repos`). This is not those tables.
- ℹ️ Remote pulls, a catalog of repos on other machines, and sister-Argus sync are [1.1](1.1-implementation.md). Not this plan.

---

## What a task is

- 🔷 Have a task, manage those tasks, run one, apply one to many machines.
- 🔷 A script can pull data.
  - Osquery is that: the task runs the query, the output comes back, another process fills the database.
- 🔷 A script can install.
  - It downloads the file from Argus, then runs the install command.
  - 💩 An Argus command line so a shell or PowerShell script can do that download over the same RPC the agent already uses.
- 🔷 Other code listens for a task finishing.
  - A notification, or it reads the output.
- ℹ️ What those scripts do matches the Texon checklist (`web.Texon/docs/plans/server-management/`): install, update, remove, or just a command.
- ℹ️ Inventory and "something new appeared" are not the task. They consume a task, or they watch.

## Schema

- 🔷 Column, SQLite type, and a short description. Not the `CREATE TABLE`.
- 🔷 Types match [4.0](4.0-data-types.md): `INTEGER` and `TEXT`.
- 🔷 `added_dt`, `updated_dt`, and `deleted_dt` are on these tables too. [4.0](4.0-data-types.md). Using them is outside this plan.
- 🔷 Stdin, stdout, and stderr stay in the current command log tree.
  - ℹ️ `localstatedir/log/argusrm/commands/yyyy/mm/dd/`.
  - ℹ️ File `{agent.id}-{identifier}` with `.stdin`, `.stdout`, or `.stderr`.
- 🔷 One task, many machines. That list is `task_target`.
- ℹ️ mtrack's `mtrack_action` is closer to `task_target`: one server, a status, a when.

### `task`

The activity. One script or command. The machines it runs on are `task_target`.

```
id                      INTEGER   row id
name                    TEXT      optional. empty for a command, or a one-off script
is_script               INTEGER   1 script, 0 one-line command
command                 TEXT      the one-line command, or a generated script
script_id               INTEGER   script.id when this task uses the library
run_as                  TEXT      optional. empty is the agent account. root, or administrator
is_template             INTEGER   1 this is a template. it is not run
is_draft                INTEGER   1 still editing. 0 approved, queued
scheduled               INTEGER   unix time to run. negative on a template
completed               INTEGER   unix time the last target finished, 0 if not
```

- 🔷 `name` is optional. You do not name a one-off command.
- 🔷 A template is a standard set you keep. Example: install the updates on the machines.
- 🔷 `is_template` is that flag. The task itself is not run. `task_target` is what runs.
- 🔷 A template uses a negative `scheduled`. It is not a time to fire.
- 🔷 Duplicate any task, including its targets, then update the copy.
- 🔷 Set the template flag and negative schedule through that update.
- 🔷 `is_script` is the script-or-command flag.
- 🔷 `command` is the one-line shell text when `is_script` is 0. A generated script body lives there too.
- 🔷 A generated script lives on the task. A library script is `script_id`.
- 🔷 `run_as` is the login this task runs as.
- 🔷 Empty is the account the agent already uses. Root, or administrator.
- 🔷 `script` is only the file. Path and repository.
- 🔷 The schedule lives on the task. Not on each machine.
- 🔷 Success does not live here. It lives on each target.

### `task_target`

One machine this task runs on.

```
id                      INTEGER   row id
task_id                 INTEGER   task.id
agent_id                INTEGER   agent.id, the machine
scheduled               INTEGER   per-target delay time. 0 means no delay
started                 INTEGER   unix time this machine started, 0 if not
ended                   INTEGER   unix time this machine finished, 0 if not
success                 INTEGER   the exit code. empty until ended
is_cancelled            INTEGER   1 cancelled. unused for now
is_watched              INTEGER   1 stream this target's output. 0 nobody is watching
timeout                 INTEGER   seconds. 0 unused for now
identifier              INTEGER   Command.identifier for this run's log files
```

- 🔷 Same script, many rows. One per machine.
- 🔷 A new task is a draft. You edit it and add machines, then approve it.
- 🔷 Before the scheduled time, approval may be toggled on or off.
- 🔷 Approval clears `task.is_draft`. Every target on that task is then queued.
- 🔷 A target's effective run time is the greater of `task.scheduled` and
  `task_target.scheduled`.
- 🔷 `task_target.scheduled` defaults to 0. It is changed only when that
  particular target must be delayed.
- 🔷 Once the scheduled time is reached, stopping work is cancellation rather
  than returning the task to draft.
- 🔷 You can queue more than one on a machine. That machine runs only one at a time.
- 🔷 The scheduler only runs targets on an approved task, and only if that
  machine is not already running one.
- 🔷 When a machine is busy, only that target is rescheduled for one minute
  later. Other machines may start immediately.
- 🔷 A library script must already be enabled on that machine. `script_agent` for this `task.script_id`.
- 🔷 A one-line command, or a generated script, has `script_id` 0. Any known agent may be a target. No `script_agent` row.
- 🔷 Run on all means every enabled machine when `script_id` is set. For `script_id` 0 it means every known agent, or a subset.
- 🔷 `success` is the exit code.
- 🔷 `is_cancelled` and `timeout` are on the row. Do not use them yet.
- 🔷 `is_watched` is 0 unless a controller asks to watch that target.
- 🔷 A watched target streams stdout, stderr, and ended to the connection that asked.
- 🔷 An unwatched target still runs. The output stays in the log files. No controller is sent that stream.
- 🔷 Returning the task to draft clears the flag.
- 🔷 Output files stay `{agent.id}-{identifier}` under the command log tree.
- 🔷 Once a target has started, its row is execution history. Normal task editing never deletes it.
- ℹ️ Retention pruning is a separate maintenance process, not part of task or target editing.
- ℹ️ mtrack put `server_id`, `status`, `when_dt`, and `results` on `mtrack_action`. Results stay in the files.

### `script`

One file in the library. mtrack's `mtrack_action_file`: a path in a repo, scanned from `bin/` and the like.

```
id                      INTEGER   row id
script_repository_id    INTEGER   script_repository.id. 0 is a file under scripts/
path                    TEXT      path in that tree, e.g. bin/apache/clear-log
filetype                TEXT      script or file
```

```
script_agent
id                      INTEGER   row id
script_id               INTEGER   script.id
agent_id                INTEGER   agent.id, this machine may run that script
```

- 🔷 A script is not valid on every machine. Enable it on a machine first. That is `script_agent`.
- 🔷 You cannot target a machine that does not have that row.
- ℹ️ mtrack's `mtrack_action_file_status` is this: the file is allowed on that server. Their create refused a script that was not active there.
- 🔷 Enablement is only `script_agent`, and only for a library script.
- 🔷 `script_id` 0 does not get a second enablement check. The target list is the permission.

### `script_repository`

A clone. Not mtrack's `mtrack_repos`. Not the local `scripts/` tree.

Two roots under `localstatedir/lib/argusrm`. Default `/var/lib/argusrm`.

- `git/{alias}` — a clone. This table.
- `scripts/` — one git repository. Created and edited here. Every save commits. Not a row in this table.

```
id                      INTEGER   row id
name                    TEXT      optional alias. empty uses the URL name
url                     TEXT      clone URL
username                TEXT      optional
password                TEXT      optional. username and password, or a key
key                     TEXT      optional. a deploy key
```

- 🔷 Clone needs a URL. Alias is optional.
- 🔷 Clone needs a username and password, or a key.
- 🔷 No description.
- 🔷 `scripts/` is a git repository. An editor save commits, so you can roll back.
- 🔷 You do not create a file on a clone. `Script.create` is only under `scripts/`.
- ℹ️ Remote-machine repos, pull requests on those folders, and sister-Argus sync are [1.1](1.1-implementation.md).

## Script or command

- 🔷 A flag says whether this is a script, or a simple command.
- 🔷 A simple command is the thin case. One line. `--command` creates that task and executes it.
- 🔷 Most real work is a script.
  - `apt-get update -y` looks like a command.
  - Headless install still needs a script to do it properly.
- 🔷 A script is a shell script, or PowerShell if that ever actually works.
- 🔷 Environment variables stay in the script.
  - We assume a shell script.
  - Setting them up in the script is enough.
- ℹ️ `Argus.Command` already has `environment` on the wire. That stays for the thin run. It is not a column on `task`.
- 💩 JSON for the task payload, or for script metadata. Named, not decided.

## Script library

- 🔷 The server has a library of standard scripts. That is `script`.
- 🔷 We already keep scripts in git.
  - `server.repositories` is the one we use now.
  - Those repos put scripts in `bin` for doing stuff on the box.
  - Some of those can form the basis of this library.
- 🔷 Enable a script on a machine before it can run there. That is `script_agent`.

## Repositories

- 🔷 `script_repository` is a clone under `git/`.
- 🔷 Local files live under `scripts/`, which is itself a git repository.
- 🔷 mtrack's `mtrack_repos` is a repository on the ticket server. Different thing.
- 🔷 The tree feeds `script`. A task is what actually runs on the agent.

## Running

- 🔷 The task is not what runs. `task_target` is.
- 🔷 Prep is a draft. Approve it, then it is queued.
- 🔷 A machine runs one target at a time. The rest stay queued.
- 🔷 A template is not run. Duplicate it, update the copy, then approve it.
- 🔷 One task, one machine, or one task on many machines. That is `task_target`.
- 🔷 For a library script, the pick list is the machines where that script is enabled. Run on all of those, or a specific set.
- 🔷 For a one-line command or a generated script, the pick list is the known agents.
- 🔷 Tasks replace the direct command. `--command` does not call `Command.run`.
- 🔷 It creates a one-line task, one target, approves it, and the scheduler runs it.
- 🔷 The code that sends the line, stores the logs, and takes stdout, stderr, and ended moves under the task.
- 🔷 The agent still receives the same run. One call per target.
- 🔷 A library script, or a generated script, is the usual case.
- 🔷 When the task ends, other code can hear it.
  - A notification.
  - Or a process that reads the output files.
- ℹ️ Office-wide software picture, Linux updates, remove, and Nagios check results are all this: a script, then something that uses the result. See [1.1](1.1-implementation.md) and [8.0](8.0-nagios.md).
