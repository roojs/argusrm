## Phase 1

The machine list, and a blank Software page. One chunk at a time. The next chunk waits until this one has been reviewed.

- 🔷 ✔️ Chunk 1. The page shell. Machines and Software on the page. Machines is empty. Software is the word Software. No grid. No filters. No server call. The window header stays the server name. `Tab.Assets`.
- 🔷 ✔️ Chunk 2. The grid, with no rows. Every one-row column is on it. A tick starts visible. Hidden starts off. A right-click on a column header shows or hides each column, the same as [5.6](5.6-agent-page.md). The last visible column stays. The column file is below. `os_updated`, `package_updated`, OS status, and S/W status stay empty until [5.10](5.10-data-enrichment.md).
- 🔷 ✔️ Chunk 3. `system_info` fills its columns, the visible ones and the hidden ones. `SystemInfo.list`. The other columns stay empty.
- 🔷 ✔️ Chunk 4. `os_version` fills its columns on the same `SystemInfo.list` reply. Name and version are the operating system. OS status and S/W status stay empty until [5.10](5.10-data-enrichment.md).
  - 🔷 `SystemInfo.list` takes a flag. The flag asks for the extra joined columns.
  - 🔷 The flag off is the call as it is now. `system_info` only. The `os_version` cells stay empty.
  - 🔷 The flag on joins `os_version` for that host. The machine list passes the flag.
  - 🔷 The joined values are properties on `SystemInfo`. They are not columns of the `system_info` table.
  - 🔷 The properties are the grid columns. `operating_system` is `os_version.name` and `os_version.version`. Then `major`, `minor`, `patch`, `build`, `platform`, `platform_like`, `codename`, and `arch`.
  - 🔷 `SystemInfo.query` has to fetch that join. `select` on `system_info` alone cannot.
  - ℹ️ `SQ.Query.select` builds `SELECT` from that table's own columns. It cannot join.
  - ℹ️ `SQ.Query.selectQuery` runs the SQL it is given. Each result column is copied onto the property of the same name. A `_` in the column name is read as `-`. A column with no property is skipped.
  - 🔷 The flag-on fetch is a `selectQuery`. `system_info` columns keep their names. `os_version.name` and `os_version.version` are one column, `operating_system`. The other `os_version` columns are selected under the property names.
  - 🚫 Do not select `os_version.id` or `os_version.agent_id`. Both tables use those names, and the second copy would overwrite the host row.
  - 🔷 A host with no `os_version` row stays on the list. Those cells are empty.
  - 🔷 The list stays one row per `system_info`.
  - ℹ️ The work is `SystemInfo.list`, `SystemInfo.query`, and `Store.SystemInfo`. No new type.
  - ℹ️ The user column is chunk 5. It is a subquery on this same flag. It is not the `os_version` join.
  - 🔷 A host has one `os_version` row. The join is on `agent_id`.
  - ℹ️ `name` and `arch` are how sync matches that row to the next snapshot. A stored row that the snapshot does not send is deleted. They are not a second operating system.
  - 🚫 Do not add a second list call for `os_version`.
  - 🚫 Do not store the joined values on `system_info`. No migration.
- 🔷 ✔️ Chunk 5. The user column. Distinct logins already stored in `logged_in_users` for that host.
  - 🔷 The cell is those names, once each.
  - 🔷 SQLite is `GROUP_CONCAT(DISTINCT logged_in_users.user)`.
  - ℹ️ `DISTINCT` takes one argument. The separator is a comma.
  - 🔷 A subquery on that host's `agent_id`. A join would repeat the machine row.
  - 🔷 The same flag as chunk 4. Flag off stays `system_info` only. The user cell stays empty.
  - 🔷 Flag on adds the subquery to that `selectQuery`. The column alias is `logged_in_users`.
  - 🔷 `logged_in_users` is a property on `SystemInfo`. It is not a column of `system_info`.
  - 🔷 The column name is `logged-in-users`. A hyphen stands in for an underscore.
  - 🔷 A host with no session stays on the list. The cell is empty.
  - 💩 A blank login is left out.
  - 🔷 The list stays one row per `system_info`.
  - 🔷 The call reads rows already stored on the server. It does not ask the agent.
  - 🔷 Other screens that need sessions read that same stored table.
  - ℹ️ How a later login reaches the server is not this chunk. Startup already posts `logged_in_users`. That refresh is the same kind of question as [5.10](5.10-data-enrichment.md).
  - ℹ️ The order of the names is whatever SQLite returns.
  - 🚫 Do not add a second list call for `logged_in_users`.
  - 🚫 Do not store the joined names on `system_info`. No migration.
  - 🚫 Do not ask the agent for this column.
- 🔷 ⏳ Chunk 6. The filter row, last. Search, OS type, and Status. Search matches the hostname and the computer name. OS type is `os_version.name`. Status is OS status and S/W status. It matches nothing until [5.10](5.10-data-enrichment.md).

## Assets — Machines

One row is the machine. Many rows are a later drill-down. The lists below stay here either way.

### One row

`system_info` and `os_version` are one row per host. These are the machine columns.

- ✅ starts visible.
- hidden starts off, and can be turned on.
- ℹ️ A tick here is the display choice. The page is not built.

`system_info`. Stored.

- ✅ `hostname` — host name.
- hidden `local_hostname` — host name without a domain.
- ✅ `computer_name` — the Windows computer name.
- hidden `uuid` — hardware UUID.
- ✅ `hardware_vendor` — maker.
- hidden `hardware_model` — model.
- hidden `hardware_version` — hardware version.
- hidden `hardware_serial` — serial.
- hidden `board_vendor` — motherboard maker.
- hidden `board_model` — motherboard model.
- hidden `board_version` — motherboard version.
- hidden `board_serial` — motherboard serial.
- ✅ `physical_memory` — bytes of RAM.
- hidden `cpu_brand` — CPU name.
- hidden `cpu_type` — CPU family code.
- hidden `cpu_subtype` — CPU subtype code.
- hidden `cpu_physical_cores` — physical cores.
- hidden `cpu_logical_cores` — logical cores.
- hidden `cpu_microcode` — microcode revision.

`os_version`. Stored. The installed system.

- ✅ `name` — Debian GNU/Linux, Windows.
- ✅ `version` — 12, 11.
- hidden `major` — first numeric part.
- hidden `minor` — second numeric part.
- hidden `patch` — third numeric part.
- hidden `build` — build string.
- hidden `platform` — debian, rhel, windows.
- hidden `platform_like` — the family. Ubuntu reports debian.
- hidden `codename` — bookworm.
- hidden `arch` — x86_64, arm64.

`os_version`, not stored yet. Filled in [5.10](5.10-data-enrichment.md). No migration. These columns are not on a server yet.

- hidden `os_updated` — when the OS version check last ran. A date.
- ✅ `os_status` — OS status. The OS version is up to date. Not the installed packages. A circle.
- hidden `package_updated` — last package update. When the package check last ran. A date.
- ✅ `package_status` — S/W status. Installed packages are up to date. A circle.
- 🔷 The headers are OS status and S/W status.
- 🔷 Green when that one is up to date.
- 💩 Red when it is not. Empty when that check has not run.

### Fake column

- ✅ Logged in users. Not a stored column. Distinct `logged_in_users.user` for that host, joined. The header is Logged in users. The column name is `logged-in-users`.
- ℹ️ The rest of that table is many rows. It is not a set of machine columns.

### Many rows

Secondary information. A later phase drills down into a machine. Not the first stage. The columns stay documented here.

`cpu_info`. One row per processor. Stored.

- ℹ️ `model` — CPU model.
- ℹ️ `manufacturer` — maker.
- ℹ️ `device_id` — which processor.
- ℹ️ `processor_type` — type code.
- ℹ️ `cpu_status` — status code.
- ℹ️ `number_of_cores` — cores on that processor.
- ℹ️ `logical_processors` — logical processors on it.
- ℹ️ `address_width` — 64 or 32.
- ℹ️ `current_clock_speed` — current MHz.
- ℹ️ `max_clock_speed` — max MHz.
- ℹ️ `socket_designation` — socket.

`logged_in_users`. One row per session. Stored. Who is logged in now. The machine cell joins the distinct `user` values. These fields are the drill-down.

- ℹ️ `user` — the login.
- ℹ️ `tty` — the terminal.
- ℹ️ `host` — where the session came from.
- ℹ️ `time` — when the session started.
- ℹ️ `type` — the kind of session.
- ℹ️ `pid` — the session process.

`interface_addresses`. One row per address. Stored.

- ℹ️ `interface` — the device name.
- ℹ️ `address` — the address.
- ℹ️ `mask` — the netmask.
- ℹ️ `broadcast` — the broadcast address.
- ℹ️ `point_to_point` — the other end, when there is one.
- ℹ️ `type` — the address family.

Not on this list.

- 🔷 Agent fields stay off the machine grid. `connected`, `last_connected`, and `ip` are on `agent`.
- ℹ️ Osquery `users` is the account list. It is not synced. The fake column is the current sessions, not an account.
- ℹ️ Osquery `uptime` is not synced.
- ℹ️ There is no power-state field.

### Shown

The columns that start visible, in order. The hidden one-row columns are on this same grid and start off.

- ✅ Logged in users. The fake column. Distinct logged-in users, joined.
- ✅ Hostname. `system_info.hostname`.
- ✅ Computer name. `system_info.computer_name`.
- 🔷 A machine shows the one it has. Hostname on a Linux host. Computer name on Windows.
- ✅ Hardware vendor. `system_info.hardware_vendor`.
- ✅ Physical memory. `system_info.physical_memory`.
- ✅ Operating system. `os_version.name` and `os_version.version`.
- ✅ OS status. `os_status`. The OS version is up to date.
- ✅ S/W status. `package_status`. Installed packages are up to date.
- ℹ️ The Agents grid already shows and hides columns from the header. [5.6](5.6-agent-page.md).
- 🔷 ⏳ Edit. Notes and the display name can be typed. The reported fields stay as reported. Notes have no column.

- 🔷 One row per host. Real and virtual machines are this list.
- ℹ️ An agent with no `system_info` is not a row here.
- ℹ️ Address and last seen are drawn in [5.5](5.5-controller-user-interface.md). They wait for the drill-down.

### Column file

- 🔷 The grid layout is a CSV. Later grids use the same file.
- 🔷 `columns/system_info.csv` is the machine grid. `Base.column_menu` reads it.
- 🔷 The first row is for reading the file. The reader ignores that row.
- 🔷 Pipes and spaces lay those names out. They are not data.
- 🔷 A blank line follows it.
- 🔷 Each later row is the column header, the database name `[JSON]`, `ON` or `off`, the width, and the format.
- 🔷 Database name `[JSON]` is that column as it is serialized. A hyphen stands in for an underscore.
- 🔷 That first line is the approved wording.
- 🔷 The first field is the column header. That text is on the grid.
- 🔷 The first data row is the row header. Logged in users. It is drawn bold.
- 🔷 The file order is the column order. The earlier order stays.
- 🔷 A blank line separates a category. Name, hardware, board, memory, CPU, the operating system, then the update pairs.
- 🔷 OS updated sits next to OS status. Package updated sits next to S/W status.
- 🔷 The reader skips an empty line. `shown` is `ON` or `off`. `ON` starts visible.
- 🔷 `text` is a label.
- 🔷 `number` is right aligned.
- 🔷 `date` is a date.
- 🔷 `status` is a circle. On or off for up to date.
- 🔷 `tick` is a tick, a cross, or empty.
- 💩 Which tick pair. Tick and cross, or tick and empty.
- ℹ️ Agents does not use this file yet. [5.6](5.6-agent-page.md).

```
Column header  |  Database name [JSON]  |  ON or off  |  Width in pixels  |  Format

Logged in users,logged-in-users,ON,180,text
Hostname,hostname,ON,180,text

Hardware vendor,hardware-vendor,ON,160,text
Hardware model,hardware-model,off,180,text

OS updated,os-updated,off,140,date
OS status,os-status,ON,120,status

Package updated,package-updated,off,170,date
S/W status,package-status,ON,140,status
```
