# 5.10 Data enrichment

**Status:** ⏳ proposed. Phase 1 is the columns. The read is phase 2, one target at a time. The flag send is phase 3.

**Pointer:** `docs/guide-to-writing-plans.md` — **Checklist for plans**.

**Parent:** [5.8-assets-page.md](5.8-assets-page.md)

---

## Purpose

- 🔷 Available packages. An installed package has an update waiting.
- 🔷 Phase 1 stores the columns. Phase 2 reads the host, by target. Phase 3 sends the change flag.
- ℹ️ An install or a removal stays a full list. [5.9.1](done/5.9.1-DONE-assets-software-data.md). The OS release is [5.11](5.11-os-update.md).
- ℹ️ Column names are [4.0](4.0-data-types.md). The software list is [5.9](5.9-assets-software.md).

---

## Phases

- 🔷 ⏳ Phase 1. The columns. `pkgs_updated` and `pkgs_status` on `os_version`. `update_available` on `deb_packages` and on `rpm_packages`.
- 🔷 ⏳ Phase 2. The read. One Linux class and one Windows class, the same split as `PackageMonitor`. APT is one target. DNF is one target. SUSE is not chosen. Windows and Android do not read a list.
- 🔷 ⏳ Phase 3. The change flag. Twice a day, and only when it changed.
- ℹ️ The machine list already has the S/W status column. It stays empty until these columns are stored. [5.8](5.8-assets-page.md).

## Phase 1

The columns. No read, and no send. There is no data to migrate. An existing database gains the column with `ALTER TABLE`. A new database gets it from `CREATE TABLE`.

- 🔷 `os_version` stores `pkgs_updated`. The last time that host checked its installed packages. Not one package.
- 🔷 `os_version` stores `pkgs_status`. Those packages are up to date.
- ℹ️ `os_updated` and `os_status` are the OS release. The server writes them. Debian's release file is [5.11](5.11-os-update.md). This plan does not read it.
- 🔷 `deb_packages` stores `update_available` on each installed package.
- 🔷 `rpm_packages` stores `update_available` on each installed package.
- 🔷 `programs` does not gain `update_available`.
- 🔷 `pkgs_updated` is the unix time of that check. The check runs twice a day. A check that finds the same answer still moves the time. `0` means the check has not happened.
- 💩 `pkgs_status` is `1` when up to date and `0` when not. `update_available` is `1` when one package has an update waiting.
- 💩 `compare` skips the three new properties. A full `OSQuery.sync` does not send them. A stored `1` against `0` would mark the row changed and clear the flag.

Edits are **Remove** / **Replace with** / **Add** from the tree. Verify the surrounding lines before applying.

### 1. `shared/OSQuery/OsVersion.vala` — `init_db`: the two columns

**Why:** the check time and the up-to-date flag have nowhere to go.

**Where:** the `CREATE TABLE` for `os_version`, on `arch`. Then the `ALTER TABLE` lines after `init_db_audit`, the same place `agent` adds a later column.

**Depends on:** none.

#### Remove

```vala
					arch          TEXT NOT NULL DEFAULT ''
				);
```

#### Replace with

```vala
					arch              TEXT NOT NULL DEFAULT '',
					pkgs_updated   INTEGER NOT NULL DEFAULT 0,
					pkgs_status    INTEGER NOT NULL DEFAULT 0
				);
```

#### Add — after `init_db_audit`, the columns on a database that already has `os_version`

```vala
			db.db.exec("ALTER TABLE os_version ADD COLUMN pkgs_updated INTEGER NOT NULL DEFAULT 0;", null, out errmsg);
			db.db.exec("ALTER TABLE os_version ADD COLUMN pkgs_status INTEGER NOT NULL DEFAULT 0;", null, out errmsg);
```

### 2. `shared/OSQuery/OsVersion.vala` — properties

**Why:** the row the agent sends, and the row the list reads, are these properties.

**Where:** after the `arch` property.

**Depends on:** ### 1.

## Phase 2

The read. The mock that stayed out of the build is not repeated. `agent/linux/UpdatesAvailable.vala` and `agent/Win32/UpdatesAvailable.vala` were written once and then removed. [2026-11-12-sync-changes-out-of-scope](../bugs/done/2026-11-12-FIXED-sync-changes-out-of-scope.md). This phase adds them to `agent/meson.build` with the class. Android compiles neither file.

- 🔷 ✔️ `OsVersion.package_manager` is the platform choice. `platform_like`, then `platform`. `APT`, `DNF`, `WIN`, or `UNKNOWN`. SUSE is `UNKNOWN`.
- 🔷 Linux is one class. `check` switches on `package_manager`. `APT` calls `check_apt`. `DNF` calls `check_rpm`.
- 🔷 Each of those returns a `Gee.ArrayList` of package names. An empty list is up to date. A failure throws.
- 🔷 Windows is the other class. It does not read a pending-update list.
- ℹ️ The helper reads the lists already on the host. It does not run the update.
- 💩 The line parser is not fenced. The command is the target below. The token that is the package name is confirmed on that target before the method is written.

### APT

Debian, Ubuntu, and eLxr. One `check_apt`. `update_available` goes on `deb_packages`.

- 🔷 The package read is `apt-get -o 'Debug::NoLocking=true' -s -qq upgrade`.
- 🔷 Each `Inst` line is one package with `update_available`. `pkgs_status` is up to date when that list is empty.
- ℹ️ `apt-daily.timer` already refreshes the lists twice a day. The agent reads that cache.
- 💩 Ubuntu uses that same read.
- 💩 eLxr uses that same read. Confirm eLxr is this family before building.

### DNF

Fedora, RHEL, and CentOS. One `check_rpm`. `update_available` goes on `rpm_packages`.

- 💩 The package read is `dnf check-update` against `/var/cache/dnf`.
- 💩 RHEL and CentOS use that same read.

### SUSE

- 💩 The package read is not `dnf`. SUSE is `zypper`. The command is not chosen. `package_manager` stays `UNKNOWN`.

### Windows

- 🔷 Windows has no file of software that needs updating. `update_available` is not added to `programs`.
- 💩 `pkgs_status` stays empty. There is no pending-update list to read.

### Android

- ℹ️ Android does not query installed packages. [5.9.1](done/5.9.1-DONE-assets-software-data.md).
- 💩 `pkgs_status` stays empty. There is no package read.

## Phase 3

The change flag. This phase does not change the full package list.

- 🔷 The agent posts the full package list with `OSQuery.sync`. An install or a removal is that list. [5.9.1](done/5.9.1-DONE-assets-software-data.md).
- 🔷 The check runs twice a day. `pkgs_updated` is that time, including a check that finds the same answer.
- 🔷 The change flag is sent when it changed. `update_available` on the package rows that flipped. `pkgs_status` on the `os_version` row when that flipped.
- ℹ️ That flag send is not built. The call is not chosen in this plan.
- 💩 The package circle comes from the same read as `update_available`, so the two do not disagree. Green when up to date, red when not. Empty when `pkgs_updated` is `0`.

## LLM notes

- 🚫 Do not monitor installs here. A package added, removed, or a version that moved is [5.9.1](done/5.9.1-DONE-assets-software-data.md).
- 🚫 Do not check whether the OS release is current. That is [5.11](5.11-os-update.md).
- 🚫 Do not paint the OS circle from `update_available`. That read is the package circle.
- 🚫 Do not replace the full package list with this flag send.
- 🚫 Do not send the flag change as a partial list through `OSQuery.sync`. A row left out of that full set is marked deleted.
- 🚫 Do not have the helper run the update. The lists are already on the host.
- 🚫 Do not add `update_available` to `programs`.
- 🚫 Do not add the read classes as a mock left out of `agent/meson.build`.
- 🚫 Do not start phase 2 before phase 1.
- 🚫 Do not mark a ✔️ line ✅.
