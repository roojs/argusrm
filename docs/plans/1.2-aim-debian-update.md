## Purpose

- 🔷 Put the server on one live machine, then update Debian boxes from the controller.
- 🔷 The path is: set up the server, open registration there, register this desktop as a controller by IP address, register an agent, log in, list the agents, select them, run system update.
- 🔷 System update is a script. The script manager holds it, and the run is a task on the selected agents.
- 🔷 Broadcast does not cross the internet. The next piece is Add IP on the registration window.
- ℹ️ The window that lists and selects is [5.5](5.5-controller-user-interface.md). The script and the task are [7.0](7.0-tasks.md) and [7.1](7.1-tasks-implementation.md).

## The path

- 🔷 `✔️` Install the server on the live machine.
  - `argusrm-server` installs, enables, and starts `argusrm-server.service`.
  - ℹ️ [install-packages.md](../install-packages.md). The unit is `packaging/systemd/argusrm-server.service`.
- 🔷 `✔️` On that server, run the controller as root.
  - It prints the six-digit number and opens the port.
  - ℹ️ The command in the tree is `sudo argus-controller --pin`. With no desktop, `sudo argus-controller` alone prints usage. [3.0 Phase 2](3.0-server.md).
- 🔷 `⏳` On this desktop, add that server and register the controller.
  - This is the next piece. See below.
- 🔷 `⏳` Register an agent against that server.
  - A box that cannot hear the broadcast still needs the server address.
  - The desktop controller is the piece specified here. The agent address waits until that window works.
- 🔷 `✔️` Log in with the certificate from that registration.
  - Saved servers are tried from `connections.json`. One that answers opens the main window over TLS.
  - ℹ️ [5.2](done/5.2-DONE-controller-user-registration.md), [5.3 Phase 1](5.3-controller-remote-registration.md).
- 🔷 `⏳` After login, list the agents.
  - `Agent.list` and `argus-controller --agents` already return the rows.
  - The window still shows the connected label. The list is the Machines grid in [5.5](5.5-controller-user-interface.md).
- 🔷 `⏳` Select the agents to update.
  - Tick the rows. The header tick selects the current filter.
  - ℹ️ [5.5 Selection](5.5-controller-user-interface.md).
- 🔷 `⏳` Run system update on that selection.
  - The action is one task, one target per selected agent.
  - What runs is the system-update script from the script manager.
  - ℹ️ `Update` on Machines in [5.5](5.5-controller-user-interface.md). `Task.create`, `Task.target`, and `Task.approve` are ready in [7.1](7.1-tasks-implementation.md).

## Script manager

- 🔷 `✔️` The server already has the library calls.
  - `Script.list`, `Script.read`, `Script.create`, `Script.update`.
  - `Script.enable` and `Script.disable` say which agents may run a script.
  - `ScriptRepository.clone`, `pull`, `list`, and `remove` are the extra libraries.
  - `scripts/` is repository id `0`.
- 🔷 `⏳` The system-update script has to be in that library before the button can run it.
  - 💩 The first copy is created in `scripts/` through `Script.create`, path `bin/debian/update`.
  - 💩 The body is the package-manager update used on these Debian boxes. The exact lines wait until this step.
- 🔷 `⏳` The controller has no page for that library yet.
  - Scripts is the first page in [5.5](5.5-controller-user-interface.md).
  - ℹ️ [7.1 Phase 3](7.1-tasks-implementation.md).
- 🔷 `⏳` Running it is the task, not a direct command from the page.
  - `--command` already runs one line on one agent. That is not this update.

## Next — add a server by IP

- 🔷 `⏳` Set up the server first. Then register the controller on this desktop.
- 🔷 `⏳` The startup popup offers adding a server. That opens the registration window.
- 🔷 `⏳` The desktop also has Add new server. That is the same window.
- 🔷 `⏳` That window is the one that scans for the broadcast and takes the six-digit number.
  - `Argus.Shared.RegisterWindow`. The controller opens it from `Bootstrap.connect_remote`.
- 🔷 `⏳` A button on that window says Add IP.
- 🔷 `⏳` Add IP reveals an IP address field, a fixed-IP tick, and Connect.
- 🔷 `⏳` The tick says this desktop is on a fixed IP. It starts unticked.
- 🔷 `⏳` A controller on a non-fixed address is not worth registering. The address changes, and it has to register again.
- 🔷 `⏳` Connect with an address and the tick left off shows a warning before anything else.
  - Using a controller on a non-fixed IP address will not work, because you will have to register again every time.
  - It is better to set up a VPN.
- 🔷 The server side stays the command line. That path does not ask about a fixed IP.
- ℹ️ The stored peer address is why a later address does not match. [6.1](6.1-nftables-firewall.md).
- 💩 After the warning is dismissed, Connect still checks the address. The warning does not refuse it.
- 🔷 `⏳` Connect checks that the address answers. It does not register yet.
- 🔷 `⏳` When the address answers, the same PIN entry appears as after a broadcast.
  - The number is the one printed on the server. There is no password prompt.
- 🔷 Broadcast stays. Add IP is how this desktop reaches a server it cannot hear.
- ℹ️ The startup page today is "Log in to local machine" and "Connect a remote machine". Connect a remote machine opens this window, which only scans.
- ℹ️ While the number is open the app port accepts the connection. [6.1](6.1-nftables-firewall.md).
- 💩 The field is an IP address. The port is the server app port unless the field includes one.
