## Purpose

- 🔷 How installed software stays in sync. Debian packages, RPM packages, and Windows programs.
- 🔷 Three phases. Phase 1 is the columns and the startup sync. Phase 2 is the package monitors. Phase 3 removed the unused `OSQuery.update` registration.
- ✔️ The startup snapshot is applied as a differential update.
- ℹ️ The list is [5.9](../5.9-assets-software.md). Filters are [5.9.2](../5.9.2-assets-software-filters.md). The machine grid is [5.9.3](../5.9.3-assets-software-machines.md). Enrichment is [5.10](../5.10-data-enrichment.md).
- ℹ️ Column names are [4.0](../4.0-data-types.md).

## Phases

- 🔷 ✅ Phase 1. The standard columns, and the standard sync. `added_dt`, `updated_dt`, and `deleted_dt` on every table. The startup snapshot writes them. The package list reads them. In `98d9f22`.
- 🔷 ✔️ Phase 2. The package monitors. One Linux class and one Windows class. `start()` reads `package_manager` after the startup snapshot. In the tree. Not watched on a machine.
- 🔷 ✔️ Phase 3. The `OSQuery.update` registration is removed. The agent posts `OSQuery.sync`.

## Phase 1 ✅

The standard columns, and the standard sync. The startup snapshot writes `added_dt`, `updated_dt`, and `deleted_dt`. The package list reads them.

### Startup snapshot

- 🔷 The agent queries `deb_packages`, `rpm_packages`, and `programs` once at startup and calls `OSQuery.sync`. This host sends about seven thousand Debian rows.
- ℹ️ Android does not query. A database copy after reboot held 7051 `deb_packages` rows for that agent.
- ✔️ The server applies that set as a differential update. `shared/OSQuery/Row.vala` `sync_rows`.
  - A stored row that differs is updated.
  - A new row is inserted.
  - A stored row the snapshot left out stays, and `deleted_dt` is set.
  - The table is not wiped and filled again.
- 🔷 ✔️ The apply writes `added_dt`, `updated_dt`, and `deleted_dt`.
- 🔷 ✔️ The names end in `_dt`. That marks a datetime. Column names are [4.0](../4.0-data-types.md).
- 🔷 ✔️ Every table has the three columns. `agent`, the osquery tables, and the task tables.
- 🔷 ✔️ They are properties on `OSQuery.Row`. `sync_rows` sets them. It does not test whether the table has the columns.
  - An insert sets `added_dt`.
  - A stored row whose columns change sets `updated_dt`.
  - A row the snapshot left out stays, and `deleted_dt` is set. That replaces the delete `sync_rows` does today.
- 🔷 ✔️ Phase 1 uses them on the package sync. Other tables carry the columns. A table that syncs through `sync_rows` gets the same writes. A table that does not sync leaves them at `0`.
- 🔷 ✔️ Each value is a unix time, `INTEGER`. `0` means that has not happened.
- 🔷 ✔️ A row that comes back after `deleted_dt` clears `deleted_dt` and sets `updated_dt`.
- 💩 ✔️ `compare` skips the three columns. The snapshot does not send them. A stored time against `0` would mark the row changed.
- ℹ️ An install time is kept when osquery already sends one. `rpm_packages.install_time` is a unix time. `programs.install_date` is text. `deb_packages` has no install time. No install column is added. A new package is found by `added_dt`.

### Controller load

- 🔷 ✔️ The default list leaves out a row whose `deleted_dt` is set.
- 🔷 ✔️ A later load passes a time. The reply is every row whose `added_dt`, `updated_dt`, or `deleted_dt` is after that time. Deleted rows are in that reply.
- ℹ️ `DebPackages.list`, `RpmPackages.list`, and `Programs.list` take `ii`: `agent_id`, `since`. [rpc-commands](../../rpc-commands.md).
- ✔️ `min_version` and `max_version` are `MIN` and `MAX` of the joined string. Debian joins `version`, a hyphen, and `revision`. RPM joins `epoch`, a colon, `version`, a hyphen, and `release`. An empty revision leaves the trailing hyphen.
- ✔️ `SELECT id FROM agent` stays on one line.
- ✔️ The added-up `WHERE` still requires `agent_id IN (SELECT id FROM agent)` and `deleted_dt = 0`.
- ✔️ 🔷 `docs/rpc-commands.md` describes `min_version` and `max_version` as the joined string.
- ℹ️ The stores still apply a full list with a client hash map. That code stays until this load exists.

## Phase 2

After the startup snapshot, a monitor watches for package changes. The watch calls `Execute.send_packages`. That posts one class through `OSQuery.sync`. `Package.sync` hashes by `pkg_name`.

- 🔷 ✔️ Linux is one class. Windows is one class. Both are `Argus.Agent.PackageMonitor`.
  - 🔷 `agent/linux/PackageMonitor.vala` and `agent/Win32/PackageMonitor.vala`. The same split as `Argus.Agent.Command`.
- 🔷 ✔️ Both files are in `agent/meson.build`. Android does not compile either one.
- 🔷 ✔️ After `send_startup`, `Application` keeps one `PackageMonitor` and calls `start()`.
- 🔷 ✔️ `start()` reads `OsVersion.package_manager`. `APT` calls `apt()`. `DNF` calls `rpm()`. `WIN` subscribes on the Windows class. Both Linux paths wait for the package lock before the rescan.
- 🚫 The monitor does not query osquery to decide the OS, and it does not test which database directory exists.
- 🔷 ✔️ The Windows class runs the Windows monitor. `start()` subscribes when the package manager is `WIN`.
- 🚫 Android has no monitor.
- 🚫 The startup sync of `deb_packages` and `rpm_packages` together, and of `programs` beside them, was rejected. A host sends one class. [2026-11-12-package-monitor-send-rejected](../../bugs/done/2026-11-12-FIXED-package-monitor-send-rejected.md).
- 🚫 `PackageMonitor.send` was rejected. The difference is `Package.sync`, hashed by `pkg_name`. `Execute.send_packages` switches on the package manager and calls `send` on that one class.
- 🚫 The package path is `OSQuery.sync`. A row left out of that full snapshot gets `deleted_dt`.
- 🚫 Do not add a `complete` flag on `sync`.
- 🚫 Do not change `Execute.select`. It stays `void`. A failed query leaves the caller's list empty.
- 🔷 ✔️ An empty new list sends nothing. It is not "every package left". `Package.send` drops it after `packages_sent`.
- 💩 ✔️ A host whose package list is really empty is cleared on the next `OSQuery.sync`, not by the monitor. An empty new list sends nothing.
- 🔷 ✔️ The difference is not found by walking every stored row for every fresh row. `Package.sync` hashes by `pkg_name`.
- 🚫 Indexing that list with `get_property` on `key_columns`, inside the monitor, was rejected. The row class builds the map from its own fields.
- ℹ️ The update columns are [5.10](../5.10-data-enrichment.md). This section is the installed rows.

### APT

- 🔷 inotify on `/var/lib/dpkg`. A change arms a deferred rescan. After the locks, the rescan calls `Application`. It does not query `deb_packages` itself.
- 💩 ✔️ The rescan waits until a non-blocking fcntl write lock succeeds on `/var/lib/dpkg/lock` and `/var/lib/dpkg/lock-frontend`. Each change restarts a one-minute timer. One send follows a quiet minute. A long maintainer script tries the lock again a minute later. `flock` does not see dpkg's lock. Not watched since that minute was added.
- ℹ️ Watched on the GNOME guest `ubuntu2604`, 2026-11-12. dpkg writes each step under `/var/lib/dpkg/updates/` and then renames `status-new` onto `status`.
  - `apt-get install hello` journalled `install ok unpacked`, then `install ok installed`, then renamed `status`. A second rename followed for the triggers. The frontend lock closed after that.
  - `apt-get remove hello` renamed `status` three times. The package was already absent at the first rename. The later renames were the triggers.
  - `hello` has no conffiles, so remove drops the row. A package with a conffile stays, status `deinstall ok config-files`, until purge.

### RPM

- 🔷 inotify on `/var/lib/rpm`. A change arms a deferred rescan. After the lock, the rescan calls `Application`. It does not query `rpm_packages` itself.
- 💩 ✔️ The rescan waits until a non-blocking fcntl write lock succeeds on `/var/lib/rpm/.rpm.lock`. That is rpm's transaction lock. Each change restarts the same one-minute timer. Not watched on a machine.
- ℹ️ The database may live at `/usr/lib/sysimage/rpm`, with `/var/lib/rpm` linked to it. The watch is the directory that holds `.rpm.lock`.

### Windows

- 🔷 The class subscribes to the Application log. The source is `MsiInstaller`. Install is event `1033` and `11707`. Removal is `1034` and `11724`. That callback is the watch. It does not search for `osqueryi` and it does not query `programs`.
- ℹ️ An exe install or a store install does not emit `MsiInstaller`. The startup snapshot still has those programs.
- ℹ️ The event is the signal. The program row comes from `programs`.
- ✔️ Each event restarts a one-minute timer. One `send_packages` follows a quiet minute.

## Phase 3

- 🔷 ✔️ `"update", "so"` is removed from `OSQuery.rpc_register` in `server/OSQuery.vala`. The comment names `OSQuery.sync` only.

### Agent to server

- 🔷 The agent posts `OSQuery.sync`. Arguments `so`: the class name, then the array. The array is the full table. It is not the rows that changed.
- 🔷 Startup posts `system_info`, `cpu_info`, `logged_in_users`, `interface_addresses`, and `os_version`, then one package class. A later package change posts that one package class again. Each call is `SELECT *` of that table.
- 🔷 The package class follows `package_manager`. APT sends `DebPackages`. DNF sends `RpmPackages`. WIN sends `Programs`. Any other value sends no package class.
- 🔷 The server applies that full array as a differential. A new `pkg_name` is inserted. A stored `pkg_name` whose columns differ is updated. A stored `pkg_name` the array left out stays, and `deleted_dt` is set. The other osquery tables do the same through `sync_rows`.
- 🔷 After the first package send, an empty package query is not posted. The machine tables are posted even when the array is empty.
- 🚫 The agent does not post a differential. The post is `OSQuery.sync`.

### Server to controller

- 🔷 The controller calls `DebPackages.list`, `RpmPackages.list`, or `Programs.list`. Arguments `ii`: `agent_id`, `since`. The reply is stored rows. It is not the agent's snapshot.
- 🔷 `since` zero is the current list. A row whose `deleted_dt` is set is left out. `agent_id` zero is one added-up row per name. `agent_id` greater than zero is that host's rows.
- 🔷 A later `since` is the differential. The reply is every stored row whose `added_dt`, `updated_dt`, or `deleted_dt` is after that time, including a deleted row. That reply is not the added-up list.
