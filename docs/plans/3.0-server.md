## Purpose

- 🔷 Build Argus in `server/`.
- 🔷 It starts up.
- 🔷 It can create a pin and show it.
- 🔷 Then the server half of enrollment, the machine record, and remote command execution.
- ℹ️ The product is [1.0](1.0-overview.md). The agent is [2.0](2.0-agent.md). The call list is [RPC commands](../rpc-commands.md).
- ℹ️ The catalog, install, uninstall, warnings, and the Debian package stay in [1.0](1.0-overview.md) until a later phase.

## Phase 1 — start up

- 🔷 `✔️` `server/` is Argus. Source for this program lives in that directory.
- 🔷 `✔️` Link `libocrpc`. Do not copy the library into this tree.
- 🔷 `✔️` The process starts up. `Initialize.fetch_osquery` runs before the sockets bind.
- 🔷 `✔️` Two sockets.
  - The app socket is the RPC. Registration, commands, identity, and warnings stay here.
  - The download socket is fixed in the Argus config.
- 🔷 `✔️` The registration response sends that download socket to the client. Index 2 of `ClientCert.request_registration`.
- 🔷 `✔️` The download socket only listens for download requests.
  - A download is a standard HTTP GET over TLS, authenticated with the client certificate.
  - The server allows or refuses that certificate.
  - The URL path is a file under the build `localstatedir`, default `/var/lib/argusrm`. A path with `..` is refused.
- 🔷 `✔️` A transfer on the download socket must not clog the app socket.
- 🔷 `✔️` Initialization fetches the latest osquery deb, rpm, and msi into `localstatedir/lib/argusrm/osquery/`, saved as `osquery.deb`, `osquery.rpm`, and `osquery.msi`. The default is `/var/lib/argusrm/osquery/`. A file already there is left in place. The GitHub body is `Argus.Server.GitHub.Release` in `server/GitHub.vala` (`Json.Serializable`, read only).
- 🚫 `Download.get` is not this fetch.
- ℹ️ `ollmfilesd/Application.vala` is the headless server that opens its listen socket. `ollmfilesd/SslListen.vala` is the TLS listen. This program is not the file daemon.
- 💩 `✔️` The executable is `argus`. Top `meson.build` calls `subdir('server')`.
- 💩 `✔️` The namespace is `Argus.Server`. `server/namespace.vala`, `server/Application.vala`, `server/Initialize.vala`, and `server/GitHub.vala`.
- 💩 `✔️` `sysconfdir/argusrm/socket` and `sysconfdir/argusrm/download` are each one `host:port` line. The default `sysconfdir` is `/etc`, so the files are `/etc/argusrm/socket` and `/etc/argusrm/download`. `--socket` and `--download` override them. With no line, the process listens on `0.0.0.0` and the build ports. The iptables class locks that listen down. See [Later](#later). `-Dsocket_port` and `-Ddownload_port` are system ports, 1–1023. The defaults are 817 and 818. The file store is `localstatedir/lib/argusrm`. The default `localstatedir` is `/var`, so the store is `/var/lib/argusrm`. `server/paths.vala.in` receives the directories and the ports from the build.

## Phase 2 — pins and enrollment

- 🔷 `✔️` `controller/` is the command-line client. Executable `argus-controller`.
- 🔷 `✔️` It creates the six-digit pin the way `PairingDialog.open` does, prints that number, and calls `ClientCert.pair` on the Unix socket.
- 💩 `✔️` That printed number is the pin. The server does not create a second one. `ClientCert.pair` stores it on `SslListen.pin`.
- 🔷 `✔️` The Unix socket is `localstatedir/lib/argusrm/argus.sock`. The default is `/var/lib/argusrm/argus.sock`.
- 🔷 `✔️` Avahi publish runs only on Argus, from `ClientCert.pair`, through `OLLMrpc.Transport.PairPublish`. An empty pin stops it. Clients browse.
- 💩 `PairPublish.start` returns false when the port is below 1024. The app port default is 817, so the publish does not go out. Registration by host and port still works while the pin is set.
- ℹ️ The pattern is `libocrpc/Transport/PairPublish.vala`.
- ℹ️ OLLMchat creates the pin in `ollmapp/SettingsDialog/PairingDialog.vala` and stores it with `ollmfilesd/ClientCert.pair`.
- 🔷 `✔️` The server accepts the pin only while that window is open. An empty `SslListen.pin` rejects the call.
- 🔷 `✔️` Sixty seconds after the pin is accepted, `argus-controller` sends an empty pin. That is the `PairingDialog` limit.
- 🔷 `✔️` Registration is `ClientCert.request_registration` in `server/ClientCert.vala`, adapted from `ollmfilesd/ClientCert.vala`. The agent already calls it.
- 🔷 `✔️` The call arguments are the pin, the certificate request, the requester, and the OS family.
  - Windows sends `windows`. Android sends `android`.
  - Debian and Ubuntu send `debian`. Fedora, RHEL, CentOS, and SUSE send `rpm`.
- 🔷 `✔️` The reply is a string array.
  - Index 0 is the client certificate PEM.
  - Index 1 is the CA PEM.
  - Index 2 is the download socket `host:port`.
  - Index 3 is the download URL path. `debian` is `/osquery/osquery.deb`. `rpm` is `/osquery/osquery.rpm`. `windows` is `/osquery/osquery.msi`. `android` is empty.
  - Later entries are listen addresses.
- 🔷 `✔️` A matching pin stores a `client_cert` row with status 1, the same approved row as `ollmfilesd`. The file is `localstatedir/lib/argusrm/argus.sqlite`.
- 💩 `✔️` The call has no machine-or-controller argument, so both registrations are that one row. The local controller is the Unix socket, not a row.
- 🔷 `✔️` Status 0 is only the open window before a row exists. `SslConnection` allows a later call when status is 1.

### Public servers

- 🔷 `⏳` The agent is installed on public servers. Those machines are usually Debian Linux.
- 🔷 `⏳` The firewall blocks public addresses. A public server stays locked down from public access. The firewall is iptables.
- 🔷 `⏳` Argus records the client IP before the agent is installed.
- 🔷 `⏳` Setting the one-time password can also take that IP, so the firewall can allow it.
- 🔷 `⏳` iptables opens for that client IP while Argus broadcasts, then locks down again after.
- 🔷 `⏳` The iptables class manages those rules. The same class locks the `0.0.0.0` listen down. See [Later](#later).
- 🔷 `⏳` The broadcast can be limited to that machine.
- 🔷 `⏳` How the agent registers remotely while that hole is open is still open.
- ℹ️ Also recorded in [1.0 Public servers](1.0-overview.md).

## Phase 3 — machine record

- 🔷 `⏳` Server records follow osquery’s data to a large degree.
- 🔷 `⏳` First data is only identity.
  - Username.
  - Computer name.
  - Type of computer.
  - Speed.
  - An identifier that can be referenced.
  - Some network information.
- 🔷 `⏳` The agent posts that with `OSQuery.sync`. One call per table. The arguments are the table name and the array of row objects.
  - Tables: `system_info`, `cpu_info`, `logged_in_users`, `interface_addresses`.
  - An empty array is sent too.
- 🔷 `⏳` Argus fills the machine record from that post.
- ℹ️ The row objects are `Argus.Shared.OSQuery`. The property name is the column name. The agent side is [2.0 Phase 3](2.0-agent.md).
- 💩 `⏳` How those rows fill the record is still open.
- 🔷 `⏳` After identity, the agent collects the installed programs and Argus stores them against the machine.
- 💩 `⏳` The programs table and the store are not this phase. See [1.0 Software](1.0-overview.md).

## Phase 4 — remote command

- 🔷 `⏳` The server tells the connected agent to run a command. That tell is a client notification, on that agent's connection.
- 🔷 `⏳` A broadcast notification goes to every connection. A client notification goes to one connection.
- 🚫 Signals and `RPC-Live-Subscribe` are not this.
- 🔷 `⏳` Every notification has a method.
- 🔷 `⏳` On the server the object is `Argus.Server.Command`. The server makes it.
- 🔷 `⏳` On the agent the object is `Argus.Agent.Command`. The two classes do not have to be the same. The server command maps to the agent command.
- 🔷 `⏳` Down the wire the object is `Argus.Command`.
  - The identifier.
  - The command.
  - The environment variables.
  - The current working directory.
- 💩 `⏳` The method that starts the command is `run`. Its argument is that one object. The agent listener already switches on `run`.
- 🔷 `⏳` A later notification can follow up on a running command. The method is `send`, with an id.
- 💩 `⏳` The id is the command `identifier` string. Arguments are `ss`: identifier, then the text. `Notification.id` is an int and is not this id.
- 🔷 `⏳` The agent sends `Command.started`. It says the command started and includes the initial output.
- 🔷 `⏳` The agent sends `Command.output`. Each call is the next chunk.
- 💩 `⏳` Both are arguments `ss`: identifier, then the text.
- 🔷 `⏳` Argus writes that output to a file.
- 🔷 `⏳` Argus then sends a client notification on the controller connection that initialized the run, when that connection is still up.
- 🔷 `⏳` A controller that initialized an install can watch that install.
- 🔷 `⏳` The type name says the controller receives it.
- 💩 `⏳` `Argus.Controller.CommandStarted` is the notification after `Command.started`. `identifier` and `text`. `text` is the initial output.
- 💩 `⏳` `Argus.Controller.CommandOutput` is the notification after each `Command.output`. `identifier` and `text`. `text` is that chunk.
- 💩 `⏳` How the server learns that the process exited was not named.
- ℹ️ The agent side is [2.0 Phase 4](2.0-agent.md). The agent does not write the file and does not send the controller objects.

## Later

Not this plan's first build. The product text is [1.0](1.0-overview.md).

- 🔷 `⏳` An iptables class manages the rules around the listen.
  - Phase 1 binds the app socket and the download socket on `0.0.0.0` and the build ports when no config line is set.
  - That class locks the listen down past `0.0.0.0`.
  - It also opens for a client IP while Argus broadcasts, then locks down again. See [Public servers](#public-servers).
- 🔷 `⏳` An online catalog categorises known software. Argus stores install files and can fetch them from an online source.
- 🔷 `⏳` A controller can add a catalog package to a machine that does not have it. Install is a download, then an install.
- 🔷 `⏳` Argus tells the agent which installed package to remove.
- 🔷 `⏳` Argus raises a warning a controller can see. A cron or shell script asks Argus whether any warning is open. The same warning can go to Android phones that have the app.
- 🔷 `⏳` The server ships the Debian package.
