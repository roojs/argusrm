# 5.2 Controller user registration

**Status:** ⏳ Phase 1 and Phase 2.1 applied — await live root/TLS activation test

**Pointer:** `docs/guide-to-writing-plans.md` — **Checklist for plans**. Proposed Vala must follow `docs/coding-standards.md`.

**Parent:** [5.1-controller-registration.md](5.1-controller-registration.md), [5.0-controller.md](5.0-controller.md), [1.0-aims.md](1.0-aims.md)

---

## Purpose

- 🔷 ⏳ Register the controller user locally or through remote pairing.
- 🔷 ⏳ Keep each server credential in the user's password storage and support multiple server connections.
- 🔷 ⏳ Use the authenticated controller identity to audit commands.
- ℹ️ [5.1](5.1-controller-registration.md) reserves id `0` for the Unix socket and defines remote controller certificates.
- ℹ️ [7.0](7.0-tasks.md) uses this identity for who created and approved a task.

---

## Phase 1 — controller identity and registration wire

- 🔷 ✔️ Add `username` and `hostname` to `Argus.Shared.Agent`.
  - `username` is the operating-system login name.
  - `hostname` is the controller machine name.
  - `is_controller` is `1` for a controller certificate.
- 🔷 One controller registration identifies one user on one machine.
- 🔷 The certificate fingerprint identifies that registration.
  - The private key proves that later requests came from that registration.
- 💩 Keep `requester` for compatibility with existing agent rows.
  - Agents continue to use it as their display label.
  - New controller code reads `username` and `hostname` instead.
- 💩 Two users on the same machine receive separate certificates and separate rows.
- 💩 The same user on two machines also receives separate rows.
- 💩 `Argus.Shared.Agent.init_db()` adds `username` and `hostname` with empty defaults.
- 💩 Existing rows do not need a data migration.
- 🔷 ✔️ Complete the explicit controller flag in the registration RPC.
  - The registration request sends `is_controller`, `username`, and `hostname` as separate fields.
  - Do not overload `requester`.
  - Do not infer `is_controller` from the OS family.
- 💩 A controller registration does not need an osquery package family.
  - The server returns an empty download path.
- ℹ️ A username is an audited local account claim.
  - Remote pairing confirms that the server operator approved the certificate.
  - It does not prove an external directory identity.

### `agent` columns

```
username                TEXT      controller login name, empty for an agent
hostname                TEXT      controller machine name
is_controller           INTEGER   1 for a controller certificate
```

## Phase 2.1 — server registration RPC and certificate issue

- 🔷 Determine root from the effective Unix user id.
  - Effective uid `0` is root.
  - Do not rely on a username string for Unix authorization.
- 💩 Do not inspect `ps`.
- 🔷 Local registration does not use the normal six-digit network pairing flow.
- 🔷 ✔️ Add `argus-controller --give-me-a-certificate USERNAME` as a root-only command-line mode.
  - The command calls a Unix-only registration RPC on the running server.
  - The RPC is `Registration.certificate` with one string username argument.
  - The server requires Unix peer uid `0`.
  - The controller username is a command-line argument.
  - The server reads the hostname from the local machine.
  - There is no certificate signing request input.
  - There is no stdin request body.
  - The running server generates the private key and certificate internally.
  - The server creates a pending `agent` row with `is_controller = 1`.
  - A missing, refused, or stale `argus.sock` produces a JSON error.
  - The command serializes the RPC result as one JSON object on stdout.
  - Success returns the private key, signed certificate, CA certificate, server name, IP addresses, and TLS port.
  - Failure returns a JSON error, including a stale socket or stopped server.

### `argus-controller --give-me-a-certificate` — privileged certificate issue

🔷 The username is the only request value. The command writes only its JSON response to stdout.
- 🔷 The serialized result is `Argus.Shared.Registration.Data`.
  - Its file is `shared/Registration/Data.vala`.
  - Do not call this object `ControllerCertificate`.

#### Add — Sample privileged call

```sh
argus-controller --give-me-a-certificate alan
```

#### Add — Sample successful response

```json
{
  "private-key": "-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n",
  "client-certificate": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n",
  "ca-certificate": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n",
  "name": "office-server",
  "addresses": [
    "192.0.2.10",
    "2001:db8::10"
  ],
  "port": 817
}
```

### Pending certificate activation

- 🔷 ✔️ The Unix registration RPC is handled by the running server.
  - No second process opens or modifies `argus.sqlite`.
- 🔷 The server creates the controller row with `status = 0`.
  - The certificate is pending and cannot authorize normal controller requests.
- 🔷 A certificate becomes valid only after the controller uses it successfully.
- 💩 Define first use as an authenticated TLS `RPC-Daemon.hello`.
  - A matching pending controller fingerprint may call only this activation request.
  - The server changes that row to `status = 1` and sets the connection's `agent_id` before replying `ok`.
- 🔷 Repeated attempts must not accumulate unused pending certificates.
- 💩 Before issuing a replacement, delete older `status = 0` controller rows with the same username and hostname.
  - Do not delete an active row.
  - The most recently issued pending certificate is the one that can be activated.
- ℹ️ `Argus.Shared.Agent.init_db()` already removes `status = 0` rows older than 24 hours.

## Phase 2.2 — controller connections and local bootstrap

- 🔷 ⏳ Load the complete controller connection list before deciding that registration is needed.
  - One connection is used directly.
  - When more than one connection exists, ask the user which one to use at startup.
  - The user may switch the active connection later.
- 🔷 Controller connection configuration belongs only to the invoking non-root user.
  - The privileged certificate command does not read or write user configuration.
  - The privileged certificate command does not access the user's password storage.
- 💩 Store connections in `${XDG_CONFIG_HOME}/argusrm/connections.json`.
  - `GLib.Environment.get_user_config_dir()` supplies `XDG_CONFIG_HOME` or its `~/.config` fallback.
  - The directory and file are owned by the controller user.
  - No root-owned controller configuration is created.
- 🔷 The JSON document is an array of serialized connection objects.
  - `Argus.Controller.Connection` is the serialized record class.
  - There is no wrapper `Config` class.
  - Each connection contains the remote data for one server.
- 🔷 Each connection contains a string `name`, a string array `addresses`, and an integer `port`.
  - One IP address is represented by a one-element array.
  - It does not contain a server id, controller username, or controller hostname.
  - Private keys, client certificates, and CA certificates are not stored in this file.

### `connections.json` — serialized connection array

🔷 The values are illustrative. The array and object fields are the required JSON shape.

#### Add — Example per-user connection file

```json
[
  {
    "name": "office-server",
    "addresses": [
      "192.0.2.10",
      "2001:db8::10"
    ],
    "port": 817
  },
  {
    "name": "lab-server",
    "addresses": [
      "198.51.100.20"
    ],
    "port": 817
  }
]
```

- 🔷 ⏳ Determine local registration from the existence of `Argus.SERVER_DATA_DIR/argus.sock`.
  - A missing socket continues to remote pairing.
  - An existing socket selects the local privileged certificate flow.
  - A stale socket is reported later by the privileged command as a server-down error.
- 💩 After storing the credential and connection, the unprivileged controller connects over TLS and sends `RPC-Daemon.hello`.
  - A crash before this step leaves only one pending row.
  - A later startup can finish activation with the stored credential.

- 🔷 The unprivileged controller only requests and receives the generated data.
- 🔷 Keep the JSON reply on the child process's standard output.
  - Standard output is the privileged command's data return channel.
  - Do not write a temporary registration bundle.
- 🔷 The unprivileged parent captures stdout rather than displaying certificate material on the terminal.
- 💩 Put the returned local server name, IP addresses, and TLS port in the connection.
  - The returned CA certificate validates the server.

## Phase 3 — local privilege hand-off

- 🔷 ⏳ When a desktop environment is present, explain that administrator access is needed and run the privileged part through Polkit.
- 💩 Detect the desktop with `DISPLAY` or `WAYLAND_DISPLAY`, matching the Linux agent.
- 💩 ⏳ Add a controller-specific Polkit action.
  - It runs only `argus-controller --give-me-a-certificate USERNAME`.
  - It does not authorize an arbitrary command.
- 💩 Keep the unprivileged controller as the parent process.
  - It receives the generated private key in the privileged JSON reply.
  - It stores the completed credential in the user's password storage.
- 🔷 ⏳ Without a desktop environment, tell the user that local registration needs root.
- 🔷 ⏳ Settle the headless root hand-off without exposing the private key.
- 💩 Preserve a user-owned parent process for password-storage access.
  - Running the whole controller as root cannot safely write to the original user's Secret Service.
  - Printing a private key for later import violates the no-file and no-terminal credential requirements.
- 💩 Preferred direction: the unprivileged parent invokes the same root command through `sudo` and captures stdout.
- 💩 Name `argus-controller --give-me-a-certificate USERNAME` in the fallback message.

## Phase 4 — password storage and server connections

- 🔷 ⏳ Store the private controller credential in the user's password storage.
- 💩 On Linux, use Secret Service through `libsecret`.
- 💩 Store one secret item per server connection.
  - Service: `argusrm`
  - Server identity: CA fingerprint
  - Username: controller login name
  - Secret: private key and signed client certificate
- 💩 Keep the CA certificate in the secret item too.
  - This prevents connection replacement from silently changing trust.
- 💩 Unlock and cancellation errors are registration failures.
  - Do not fall back to a plaintext PEM.
- ℹ️ There is no keyring or `libsecret` implementation in the tree yet.
- 🔷 ⏳ Store non-secret connection data in the Phase 2 per-user JSON file.
- 🔷 ⏳ Support more than one controller/server registration.
- 💩 Use one connection object per server name.
  - Store the display name, IP addresses, and TLS port.
  - Do not store a private key or certificate PEM in this directory.
- 🔷 Ask which connection to use when more than one exists.
  - A later UI may switch the active connection.
  - The CLI may gain an explicit connection selector.
- 💩 Registration must not overwrite another server's connection or secret.
- 💩 Use the server name and CA fingerprint when matching a connection to its password-storage item.
- 🔷 A user is registered for one server only when both the connection and its matching password-storage credential exist.
- 💩 A connection without a credential is incomplete and must not silently fall back to an unauthenticated connection.
- 💩 A credential without a connection may be removed during an explicit repair flow, but not during normal startup.
- 💩 Registration is per server connection, not one global boolean.

## Phase 5 — remote pairing

- 🔷 ⏳ If no local server is running, tell the user to enable registration on the remote server.
- 🔷 ⏳ Browse for the server, ask for its registration number, and request a controller certificate.
- 🔷 The remote pairing request includes the controller user's `username` and the controller machine's `hostname`.
  - Send them as separate registration fields.
  - Set `is_controller` explicitly.
- 🔷 Store the result through the Phase 4 password-storage and connection path.
- ℹ️ The wire flag and remote flow start in [5.1 Phase 1b and Phase 2](5.1-controller-registration.md).

## Phase 6 — authenticated use and audit identity

- 🔷 ⏳ Make commands attributable to the authenticated user certificate.
- 💩 ⏳ After registration, use TLS with the active connection even when the server is on the same machine.
  - The server maps the certificate fingerprint to the controller `agent.id`.
  - The Unix socket remains the bootstrap and privileged maintenance path.
- 💩 This supersedes the [5.1 Phase 3](5.1-controller-registration.md) suggestion to prefer the Unix socket whenever it exists.
  - A normal Unix request is controller id `0`.
  - It cannot identify which desktop user requested a command.
- 💩 A controller deliberately run as root on the Unix socket is audited as local system control, id `0`.
- 💩 ⏳ Retain the caller controller `agent.id` with each command identifier and target agent id.
- 💩 Store immutable ids rather than only copied username text so later display changes do not rewrite history.
- 💩 The persistent audit row belongs with the command/task schema.
  - Thin `Command.run` needs controller id, target id, identifier, and request time.
  - A task needs creator and approver controller ids in [7.0](7.0-tasks.md).
- ℹ️ Registration provides the authenticated identity but does not itself add the command or task audit columns.

## LLM notes

- 🚫 Do not use `ps` to decide whether this is the local server.
- 🚫 Do not insert an `agent` row with id `0`.
- 🚫 Do not write a controller private key under `Argus.AGENT_DATA_DIR`, the user data directory, or `~/.config/argusrm/`.
- 🚫 Do not reuse the agent's root-owned certificate as the user's controller identity.
- 🚫 Do not infer `is_controller` from the OS family.
- 🚫 Do not claim per-user audit while normal local commands still use the anonymous Unix controller id `0`.
