## Purpose

- 🔷 Nagios, on these servers, is a set of scripts.
- 🔷 Run all of them. The output is data in this application.
- 🔷 A result that is not OK is fixed by a script.
- 🔷 That pairing was the original aim of MTrack.
- ℹ️ The checks and the fix scripts already live in the server repositories. `server.global` and `server.media-outreach`.
- ℹ️ MTrack's Service Issues screen is the picture. Status on one side. The matching `bin/` scripts on the other. Run the script. Then read the check again.

---

## The checks

- 🔷 A check is a command already on the machine.
- ℹ️ NRPE files under `etc/nagios/nrpe.d/` are one line each. `command[name]=` the line to run.
- ℹ️ The plugins sit in `/usr/lib/nagios/plugins/`. The same trees are in the repos as `etc/nagios/` and `usr/lib/nagios/`.
- ℹ️ Examples already on the boxes:
  - `check_disk` on `/`
  - `check_apt`
  - `check_php_errors`
  - `check_git_status.php`
  - a PHP report invoked as the check command, such as missing clippings
- 🔷 Run every one of those lines.
- 🔷 One machine, or the same check on many machines. That is a task. [7.0](7.0-tasks.md).
- 💩 The sweep reads the `command[` lines from `nrpe.d` on that agent. Confirm before build.
- 💩 Some lines already say `sudo -u` and a user. `run_as` on the task is the other place that chooses the account. Confirm which one owns it.

---

## The output

- 🔷 The application keeps what the script printed, and whether it passed.
- ℹ️ A Nagios plugin exits 0 for OK, 1 for warning, 2 for critical, 3 for unknown.
- ℹ️ The first line is the short text. Further lines are the detail. Text after `|` is performance data.
- ℹ️ MTrack stored the same three pieces on `mtrack_service`: `nagios_status`, `nagios_status_head`, `nagios_status_desc`, plus `last_status_update`.
- 🔷 Same idea here. One row per check per machine. The controller can list it.
- ℹ️ A task already keeps stdout, stderr, and the exit code in the command log. [7.0](7.0-tasks.md).
- ℹ️ Something that hears the task finish fills the row. Osquery is that shape: the task runs, another process stores the output.
- 💩 The table is not in [7.0](7.0-tasks.md). Leave the task schema alone. Name the columns when this plan is confirmed.
- 💩 Keep the performance data on the row. Drawing it can wait.

---

## The fix

- 🔷 The fix is a script from the library, run as a task on the machines that failed that check.
- ℹ️ MTrack chose the scripts with the last word of the service name. `apt` offered `bin/apt/`. `php-error` offered `bin/apache/`.
- ℹ️ `server.global/bin/apache/remove_php_errors.sh` prints the matching log lines, so the runner can store them, then deletes those lines.
- 🔷 Several machines with the same check can take the same script.
- ℹ️ MTrack refused the run when the ticked rows were not the same check.
- 🔷 When that task ends, run the check again. The row becomes the new output.
- 💩 Keep MTrack's name rule, including `php-error` mapping to `bin/apache/`. Confirm the exceptions before build.
- 💩 The fix script has to be enabled on that agent first. That is `script_agent`. [7.0](7.0-tasks.md).
