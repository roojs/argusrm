## Purpose

- 🔷 `⏳` Keep the controller viewable while locked. Unlock a live mode to execute, then lock it again.
- 🔷 `⏳` Examine whether the Linux daemon can run as a dedicated user.
- 🔷 `⏳` Elevate only operations that require root access.
- 🔷 `⏳` Compare the security benefit with the current root daemon.
- 🔷 `⏳` Decide whether the privilege split is feasible before specifying implementation changes.
- 🔷 `⏳` Examine whether the Argus server daemon also needs to run as root.
- 🔷 `⏳` Prefer dropping or avoiding server root privileges after privileged startup work.
- ℹ️ This is a temporary decision plan. It contains no code proposal.

## Controller live mode

- 🔷 `⏳` Startup uses the controller certificate to talk to the server. That connection stays up.
- 🔷 `⏳` Locked is the normal mode. The user can look around and view tasks, scripts, and machines.
- 🔷 `⏳` Live mode is for changes that execute work: schedule, approve, run.
- 🔷 `⏳` Entering live mode authenticates this same user again and unlocks the action secret.
- 🔷 `⏳` The process keeps that uid. The prompt is this user's login, Polkit `auth_self` or a Secret Service unlock.
- 🔷 `⏳` One unlock covers a run of those actions.
- 🔷 `⏳` The user can lock it again. Locking closes the action secret and returns to view-only.
- 🔷 `⏳` Leaving the desktop locks it too. A desktop left on returns to view-only.
- 🔷 `⏳` A cancel or a failed unlock stays locked.
- 💩 Whether the action secret is a second certificate, or a signing key stored beside the connection credential in [5.2](5.2-controller-user-registration.md). Startup already has the connection certificate.
- 💩 How long live mode stays open before the idle lock. Long enough for a run of tasks.
- ℹ️ The signatures later in this plan grant a root job on a machine. This lock is the person at the controller.
- ℹ️ [7.0](7.0-tasks.md) is where schedule, approve, and run land.

## Current privilege boundary

- ℹ️ `packaging/systemd/argusrm-agent.service` has no `User=`, so systemd runs the service as root.
- ℹ️ The proposed SysV script in `docs/plans/2.1.5-installation-packaging.md` also starts the service as root.
- ℹ️ `agent/linux/Application.vala` rejects non-root `--service` execution.
- ℹ️ The root process owns the machine certificate and key under `/var/lib/argusrm-agent/argus`.
- ℹ️ Most steady-state work does not inherently require root:
  - TLS connection and notification parsing.
  - Downloading files.
  - Running the current osquery inventory queries.
  - Sending inventory and command output.
- ℹ️ Current root-required work is:
  - Enabling, starting, and restarting the service during registration.
  - Installing osquery with `dpkg` or `rpm`.
  - Running remote Linux commands through `sh -c` when those commands need root access.
- ℹ️ The last item is not a narrow administrative operation. `agent/linux/Command.vala` currently defines a general remote root shell.

---

## Security finding

- 💩 Running the network-facing daemon as a dedicated user is technically feasible.
- 💩 It materially reduces risk only when the privileged interface is narrower than the daemon's current `sh -c` command interface.
- 💩 A dedicated user would contain defects in:
  - TLS and socket handling.
  - RPC and notification deserialization.
  - Download handling.
  - Inventory collection.
  - General daemon control flow.
- 💩 With a real privilege boundary, compromise of those paths would initially grant the `argusrm-agent` account instead of immediate root access.
- 💩 It would also reduce accidental damage from path, environment, and process handling bugs.
- 💩 The dedicated account would still expose:
  - The machine private key and management identity needed by the daemon.
  - Inventory visible to that account.
  - Any files and processes deliberately made available to managed commands.
- 💩 A root helper must not authorize a job merely because it came from the dedicated daemon.
  - A Unix socket peer check, sudoers entry, or permissive Polkit rule that trusts `argusrm-agent` would let a compromised daemon authorize its own root jobs.
  - A signed, single-use server grant bound to the exact job prevents the daemon from authorizing or altering a root command.
- 💩 Prompting through Polkit is not suitable for unattended management. A non-interactive allow rule is equivalent to granting the allowed helper operations to the daemon account.
- 💩 Running the whole daemon as root remains a defensible product choice only if arbitrary unattended root command execution is an explicit requirement. It leaves every remotely reachable daemon defect in the root trust boundary.

## Feasible designs

### 1. Root daemon with systemd hardening

- 💩 Keep the current privilege model and add compatible service protections.
- 💩 This is the smallest change, but the daemon and remote shell remain root.
- 💩 Potentially compatible controls need testing:
  - A private temporary directory.
  - Restricting device access.
  - Restricting kernel tunables, control groups, and namespaces.
  - Removing capabilities that managed commands never need.
- 💩 Strong filesystem, syscall, capability, or `NoNewPrivileges` restrictions may conflict with software installation and general root commands.
- 💩 This option lowers some impact but does not create a privilege boundary.

### 2. Dedicated daemon with allowlisted privileged operations

- 💩 Run networking, parsing, downloads, inventory, and normal commands as `argusrm-agent`.
- 💩 Keep registration service setup in the separately elevated registration process.
- 💩 Permit a small root helper to perform typed operations such as:
  - Install the authenticated osquery package.
  - Restart the agent service.
- 💩 Do not pass shell command strings, arbitrary paths, caller-controlled environments, or caller-controlled working directories to this helper.
- 💩 Run remote commands as `argusrm-agent` unless a separately designed privileged operation covers the request.
- 💩 This provides the strongest straightforward reduction in daemon risk.
- 💩 It changes the present expectation that every remote command runs as root.

### 3. Dedicated daemon with signed, single-use root jobs

- 🔷 Let the root helper accept an arbitrary command only after the management server authorizes that exact command.
- 🔷 Establish signing trust when the machine is registered.
- 🔷 Use a one-off authorization for each root command.
- 🔷 The helper may keep a live challenge or ephemeral key only in memory and exit after starting or completing the authorized command.
- 💩 Do not give an authorization secret to the unprivileged daemon.
  - The daemon transports requests and replies.
  - It must not possess a key that can mint a root authorization.
- 💩 Use two signing directions if the server must know that a challenge came from the real root helper:
  - The helper generates a machine authorization key during registration.
  - Its private key remains root-only.
  - Its public key is uploaded to the server.
  - The helper signs each challenge with the machine private key.
  - The server signs each grant with a server authorization key.
  - The server public key is pinned in root-owned helper state.
- 💩 The keys have different purposes.
  - The machine key proves that the helper created the challenge.
  - The server key proves that the server granted the exact root job.
  - The existing daemon TLS key should not grant either authority.

#### Signed envelope option

- 💩 The server can send a signed job without a second round trip.
- 💩 The signed payload must bind every execution-relevant field:
  - Protocol version and authorization purpose.
  - Machine identity and server identity.
  - Job identifier and controller-approved request identifier.
  - Exact command or argument vector.
  - Environment and working directory.
  - Creation time, expiry, and maximum runtime.
  - Whether stdin is closed or interactive.
  - Hashes of any downloaded package, script, or executable.
- 💩 The helper verifies the signature, expiry, machine, and unused job identifier before executing it.
- 💩 A root-owned replay ledger is still required because a captured signed envelope remains valid until it expires.
- 💩 This is simpler than a live challenge, but authorization can be copied and replayed unless the helper reliably records consumption.

#### Challenge-response option

- 💩 A one-shot helper can generate a cryptographically random nonce and keep it only in memory.
- 💩 Proposed flow:
  - The server records a controller-approved root job.
  - The daemon passes the exact job to the helper.
  - The helper canonicalizes it and calculates its digest.
  - The helper creates a nonce and signs a challenge containing the machine, job identifier, digest, and nonce.
  - The daemon relays that challenge to the server.
  - The server verifies the helper signature.
  - The server grants only a matching, already-approved job.
  - The server signs the digest, nonce, machine, job identifier, and short expiry.
  - The helper verifies the grant and executes the exact challenged job once.
  - The helper records the job as consumed and exits.
- 💩 The server must not sign a new command merely because the daemon requested it.
  - Authorization must originate from an approved controller job.
  - Otherwise a compromised daemon could use the signing service as a root command oracle.
- 💩 The nonce proves freshness while the helper is alive. The root-owned consumed-job record protects crash and restart boundaries.
- 💩 This best matches the proposed one-off key idea without placing a reusable authorization secret in the daemon.

#### One-time bearer token option

- 💩 The server could issue an opaque token that the helper validates online.
- 💩 This requires the root helper to contact the server or share a validation secret.
- 💩 A token observed by the daemon is bearer authority until consumed.
- 💩 Binding the token to the complete job, machine, nonce, and expiry reduces the risk, but a signed challenge-response gives clearer trust separation.

#### Direct helper-to-server option

- 💩 The root helper could authenticate directly to the server with its root-only machine key and fetch the approved job.
- 💩 This avoids trusting the daemon as the authorization transport.
- 💩 It also moves TLS, network, and response parsing back into a root process.
- 💩 A short-lived outgoing connection limits exposure but makes the root helper larger than an offline signature verifier.

#### Execution boundary

- 💩 Signing the command text alone is insufficient.
  - Unsigned environment, working directory, or interpreter fields can change what runs.
  - A signed script path is unsafe when the daemon can replace that script.
  - A package pathname is unsafe without a signed content digest and a race-safe file handoff.
- 💩 The protocol needs one canonical byte representation. The helper must verify and execute the same parsed object rather than reconstructing a shell string after verification.
- 💩 If shell syntax is required, the signed payload must explicitly bind the shell executable and exact command string.
- 💩 Current follow-up stdin in `agent/linux/Command.vala` needs special treatment:
  - Arbitrary stdin to an authorized root shell restores arbitrary root access to a compromised daemon.
  - Non-interactive root jobs should close stdin.
  - An authorized interactive root session deliberately suspends containment for that session and must be represented as a separate permission.
- 💩 This design contains compromise of only the unprivileged daemon. It does not protect against compromise of:
  - The management server authorization key.
  - The controller approval path.
  - The root helper or its machine private key.

## Packaging and data implications

- 💩 `⏳` If a dedicated daemon is selected, define a system account with no interactive shell and no home directory.
- 💩 `⏳` Make `/var/lib/argusrm-agent` and `/var/log/argusrm` writable only where the daemon requires it.
- 💩 `⏳` Let systemd create and own state and log directories for the service user.
- 💩 `⏳` Add equivalent account, directory ownership, and privilege dropping to Debian, RPM, and SysV packaging.
- 💩 `⏳` Decide whether the daemon account owns the machine private key.
  - The daemon needs to use it for TLS in the current architecture.
  - Keep that TLS identity separate from the root-helper authorization keys.
- 💩 `⏳` Store the helper machine private key, pinned server authorization public key, and replay ledger in a root-only state directory.
- 💩 `⏳` Define authorization-key enrollment, rotation, revocation, backup, and server-recovery behavior.
- 💩 `⏳` Replace the shared temporary installer pathname with a protected, non-symlink-following handoff before any root helper installs a file.
- 💩 `⏳` Define upgrade behavior before changing ownership of an existing root-owned installation.

## Server daemon

### Current server privileges

- ℹ️ `packaging/systemd/argusrm-server.service` has no `User=`, so the server currently runs as root.
- ℹ️ The server does not check for root and can otherwise run as any user that can access its state, logs, configuration, and sockets.
- ℹ️ The default app and download ports are 817 and 818. Linux normally requires root or `CAP_NET_BIND_SERVICE` to bind those ports.
- ℹ️ `StateDirectory=argusrm`, `ConfigurationDirectory=argusrm`, and `LogsDirectory=argusrm` already let systemd prepare the server directories.
- ℹ️ Planned Phase 5 firewall changes in `docs/plans/3.0-server.md` require continuing privilege after startup because registration opens and restores rules while the server is running.

### Drop privileges after binding

- 🔷 The server could start as root, bind ports 817 and 818, then change to a dedicated account.
- 💩 A correct internal drop would need to:
  - Initialize supplementary groups.
  - Set the dedicated group before setting the user.
  - Make the drop irreversible.
  - Occur before accepting any network connection.
  - Preserve access to the database, package store, logs, Unix socket, and TLS keys.
- 💩 This is feasible but is not the preferred systemd design.
- 💩 Current startup performs network and parser work before the listeners bind:
  - `Initialize.fetch_osquery()` requests GitHub release JSON.
  - It downloads installers.
  - TLS material and database state are initialized.
- 💩 Dropping only after the ports bind therefore performs avoidable network parsing and filesystem work as root.
- 💩 A one-time privilege drop also cannot perform the planned runtime iptables changes without retaining a powerful capability or calling a privileged helper.

### Dedicated server account from process start

- 💩 Prefer running the complete server as a dedicated `argusrm-server` account from its first instruction.
- 💩 For ports 817 and 818, give only the bind capability in the systemd unit:
  - `CapabilityBoundingSet=CAP_NET_BIND_SERVICE`.
  - `AmbientCapabilities=CAP_NET_BIND_SERVICE`.
  - `NoNewPrivileges=true`.
- 💩 Remove the bind capability after both listeners are open if the selected implementation can do so safely.
- 💩 An alternative is to move both listeners above port 1023 and grant no capability.
- 💩 Systemd socket activation could bind privileged ports without granting the daemon a capability. The current Vala listeners do not consume inherited systemd sockets, so this is a larger implementation change.
- 💩 Keep firewall mutation outside the server process:
  - Use a narrow root helper with typed add, remove, open-registration, and restore operations.
  - Validate addresses, protocol, ports, and rule ownership in the helper.
  - Do not grant `CAP_NET_ADMIN` to the network-facing server.
- 💩 `CAP_NET_ADMIN` is broad enough to reconfigure routing and firewall state. Giving it to the server would weaken much of the dedicated-user benefit.

### Firewall privilege broker

- 🔷 Use a separate privileged process for firewall management.
- 🔷 Let the unprivileged server request a temporary privileged firewall operation when registration opens, closes, or records an address.
- 💩 Do not let the server process temporarily elevate itself.
  - Retaining a saved root identity, set-user-ID path, or `CAP_NET_ADMIN` gives compromised server code the same route back to privilege.
  - An irreversible privilege drop followed by a separate broker preserves the process boundary.
- 💩 Prefer a root-owned, system-D-Bus-activated firewall broker:
  - D-Bus policy permits calls only from the `argusrm-server` service account.
  - The broker exposes typed methods rather than command strings.
  - Activation starts the root process only when a firewall change is required.
  - The broker exits after applying a normal operation.
  - The broker remains alive through a temporary registration window when it must enforce automatic closure.
- 💩 A root-owned systemd one-shot service is another option, but dynamic addresses and registration state need a safe typed handoff rather than command-line interpolation.
- 💩 Avoid making the firewall executable set-user-ID and avoid a broad sudoers rule.
- 💩 The broker API should be limited to Argus-owned policy:
  - Initialize the dedicated Argus chain and its jump from the host input chain.
  - Replace the registered-address allowlist.
  - Add or remove one validated IPv4 or IPv6 address.
  - Open only the Argus app port for a registration window.
  - Restore the registered-address policy.
  - Remove only rules carrying the Argus ownership marker during uninstall.
- 💩 The broker must not accept:
  - Raw iptables arguments.
  - Shell text.
  - Arbitrary chain or table names.
  - Arbitrary ports or protocols.
  - Paths supplied by the server.
- 💩 The broker should validate addresses with a real address parser and construct rules internally using fixed executable paths and a fixed environment.
- 💩 The registration-open operation needs a broker-enforced maximum lifetime:
  - The current registration window is 60 seconds.
  - The broker must restore the allowlist when that deadline expires even if the server crashes, disconnects, or is killed.
  - A close request may restore the allowlist earlier.
- 💩 The broker should apply complete rulesets atomically so a failure does not leave a partially open policy.
- 💩 The broker protects host root privilege from a compromised server, but a broker that trusts the server account cannot fully protect firewall policy from that compromised account.
  - A compromised server could request the permitted open-registration operation repeatedly.
  - A broker-enforced duration limits accidental or abandoned exposure.
  - Requiring a separate controller authorization for opening registration would create a stronger policy boundary if that threat is in scope.
- 💩 Log the caller identity, operation, validated addresses, result, and registration expiry without accepting caller-supplied log text as trusted data.

### Firewall broker D-Bus access control

- 🔷 Restrict firewall broker access to the Argus server process and already-privileged processes.
- 🔷 A dedicated server UID, system-bus policy, and broker-side D-Bus credential check are sufficient for this narrow firewall interface.
- 💩 Use the system bus, not a session bus.
- 💩 Install a default-deny system-bus policy for the broker destination, object path, interface, and methods.
  - Allow calls from the dedicated `argusrm-server` Unix user.
  - Allow calls from root for administration and recovery.
  - Deny all other users by default.
- 💩 Restrict ownership of the broker's well-known bus name to root.
- 💩 Run the activated broker from a root-owned executable and root-owned systemd unit that unprivileged users cannot replace or edit.
- 💩 Do not treat possession of a well-known caller bus name as authentication.
  - A name can disappear and be reacquired.
  - The broker must use the unique sender name attached by the bus daemon.
- 💩 For every call, resolve the unique sender through `org.freedesktop.DBus.GetConnectionCredentials` and verify:
  - `UnixUserID` is the dedicated `argusrm-server` UID or root.
  - `ProcessID` exists for audit.
- 💩 The bus daemon obtains Unix credentials from the kernel connection. Caller-supplied method arguments must never provide the claimed UID, PID, or security label.
- 💩 Give the `argusrm-server` UID to no other daemon, login, maintenance task, or package.
- 💩 Run no untrusted child process as `argusrm-server`.
- 💩 UID authorization proves that the caller runs as the server account; D-Bus alone does not prove that it is a particular executable.
- 💩 Exact executable identity and signed firewall grants are unnecessary for this broker because its methods can only modify the fixed Argus firewall policy.
- 💩 The process ID is audit evidence, not the authorization boundary, because processes can exit and PIDs can be reused.
- 💩 The narrow typed broker API remains required even with perfect caller authentication.
  - Authentication decides who may request an operation.
  - Validation limits what an authenticated or compromised server can make root do.

### Server data boundary

- 💩 The dedicated account needs read and write access to:
  - `/var/lib/argusrm/argus.sqlite`.
  - `/var/lib/argusrm/packages`.
  - `/var/lib/argusrm/argus.sock`.
  - `/var/lib/argusrm/tls`.
  - `/var/log/argusrm/server.log`.
- 💩 `/etc/argusrm` should remain root-owned and only readable by the server.
- 💩 The Unix controller socket needs an explicit owner, group, and mode. Its filesystem permissions are part of controller authorization.
- 💩 Compromise of an unprivileged server would still expose the database, packages, connected agents, and any signing keys readable by that account. It would not automatically grant root on the server host.

### Certificate authority finding

- ℹ️ `server/Application.vala` currently creates `/var/lib/argusrm/tls/ollmrpc-ca-key.pem` by copying `/ollmrpc/ollmrpc-ca-key.pem` from a compiled resource.
- 💩 `⏳` Replace the packaged CA private key with a unique CA key generated on each server installation.
- 💩 A CA private key distributed in program resources is not secret. Anyone with the same resource can mint a client certificate trusted by a server using that CA.
- 💩 Generate the CA key directly into the server state directory with restrictive permissions.
- 💩 Decide whether the unprivileged server may read that key:
  - Keeping it in the server process is simpler but lets a server compromise mint client certificates.
  - A narrow certificate-signing helper or external key store preserves a stronger signing boundary.
- 💩 Keep the root-job authorization key separate from the TLS CA key.

## Decision required

- 🔷 `⏳` Decide whether arbitrary remote commands must run as root.
- 🔷 `⏳` Decide whether server ports 817 and 818 must remain below 1024.
- 💩 If the answer is no:
  - Select design 2.
  - Make unprivileged execution the default.
  - Add only typed, allowlisted privileged operations.
- 💩 If the answer is yes:
  - Select design 1 as the simple, explicit trust model.
  - Or select design 3 to contain compromise of the unprivileged daemon.
- 💩 Within design 3, prefer signed challenge-response:
  - The helper signs a fresh challenge.
  - The server signs only a matching, previously approved job.
  - The helper executes that exact job once.
- 💩 Run the server as `argusrm-server` from process start.
- 💩 Grant only `CAP_NET_BIND_SERVICE` when the low ports remain.
- 💩 Put dynamic firewall changes behind a D-Bus-activated privileged broker with typed operations and broker-enforced registration expiry.
